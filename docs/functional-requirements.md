# Functional Requirements

Detailed functional requirements for Open Garden Planner. These serve as the specification for implementation.

## FR-1: Canvas and Coordinate System

### FR-1.1 Metric Canvas
- **FR-CANVAS-01**: Canvas uses metric coordinate system (centimeters as base unit)
- **FR-CANVAS-02**: Display can show measurements in cm, m, or mixed (e.g., "2.35 m")
- **FR-CANVAS-03**: Canvas supports zoom from 1:1000 (overview) to 1:1 (detail) scale
- **FR-CANVAS-04**: Pan and zoom via mouse wheel, drag, and keyboard shortcuts

### FR-1.2 Grid System
- **FR-GRID-01**: Optional visible grid overlay (toggleable via toolbar button)
- **FR-GRID-02**: Grid spacing configurable (10cm, 25cm, 50cm, 100cm)
- **FR-GRID-03**: Snap-to-grid toggleable (independent of grid visibility)
- **FR-GRID-04**: Grid renders efficiently at all zoom levels (adaptive detail)

### FR-1.3 Background Image
- **FR-IMG-01**: Import background images (PNG, JPG, TIFF)
- **FR-IMG-02**: Calibrate image scale by marking a known distance (e.g., "this fence is 5.2m")
- **FR-IMG-03**: Two-point calibration: user clicks two points and enters the real-world distance
- **FR-IMG-04**: Adjust image opacity (0-100%)
- **FR-IMG-05**: Lock/unlock image layer to prevent accidental movement
- **FR-IMG-06**: Image stored as reference in project (path or embedded, user choice)
- **FR-IMG-07**: Multiple background images supported (e.g., different areas of property)
- **FR-IMG-08**: Load satellite imagery directly from Google Maps via an embedded picker dialog: address search (Places Autocomplete), navigate the map, drag a rectangle, fetch via Static Maps API. Available when a key is configured in Preferences (`api_keys/google_maps_key`) or through the `OGP_GOOGLE_MAPS_KEY` environment/`.env` fallback; a non-empty Preferences value takes precedence (ADR-019, Issue #342). When the Static API rejects the satellite request with the Google-canonical EEA 403 (“not available for your account and region”), the picker offers — and always provides via a “Capture view” action — a JS-API view capture: the live map is positioned over the rectangle, the embedded web view is grabbed at the widget level, and the image is scaled/cropped analytically (ADR-019 addendum #346).
- **FR-IMG-11**: The JS-API view capture raises the Static-mosaic resolution ceiling for large gardens: for rectangles wider than the map viewport at the best zoom, the picker pans the embedded map across up to a 3×3 grid of viewport positions at one integer zoom, grabs each frame, and stitches them seamlessly at analytic whole-pixel offsets; the result is cropped to the drawn rectangle and carries exactly one attribution strip regardless of grid size. Per-frame rendering failures are retried (2 attempts) and then fail with a clean message — a partially blank import is never accepted (ADR-019 addendum #347).
- **FR-IMG-09**: Satellite imports land on the canvas at true real-world scale automatically (no manual two-point calibration), with `meters_per_pixel` derived analytically from the Web-Mercator zoom level and latitude. The manual `Calibrate Scale…` context-menu action remains available as an override.
- **FR-IMG-10**: Satellite imports persist in the `.ogp` project file with geo metadata (center, NW/SE bbox corners, zoom, source, timestamp) — older projects without this metadata continue to load unchanged. JS-capture imports additionally persist `source: google_js_view_capture` and an `attribution` line (additive keys, Issue #346).

### FR-5.3 Plant Database Integration
- **FR-PLANT-10**: Connect to Trefle.io API for plant species lookup (primary)
- **FR-PLANT-11**: Offline mode: cache previously fetched plant data locally (SQLite)
- **FR-PLANT-12**: User can create custom plant species entries (stored in local library)
- **FR-PLANT-13**: Search plants by common name, scientific name, or characteristics
- **FR-PLANT-14**: Species search first queries the complete bundled/custom offline catalog, then applies the text and trait filters before the display limit. Empty or filter-only browsing stays offline. A nonempty query with zero filtered offline matches automatically invokes the configured online fallback chain; **Search online** invokes it explicitly even when local matches exist. Online requests and selected-result enrichment run away from the GUI thread, with obsolete query/selection/closed-dialog responses discarded.

  The existing `PlantAPIManager.search()` online fallback still searches custom entries before Trefle, Perenual and Permapeople. It does not deduplicate custom-library results against provider results. Every result row shows its source (FR-PLANT-18), distinguishing a reusable user record from a fetched record. The bundled catalog is available through the shared offline search service rather than a new network-manager client.
- **FR-PLANT-19** *(issue #302)*: A plant search that every reachable database answers with **zero matches is not an error** and must never be reported as one. `PlantAPIManager.search()` raises `PlantAPIError` only when *no* configured provider answered at all (every one raised) and the custom library had no hit; if at least one provider answered — even with an empty list — the honest result `[]` is returned. `PlantSearchDialog` then shows a warning-coloured status *"No plants matched '{query}'. Try another spelling or the scientific name."* with **no modal dialog**, or *"No plant databases are configured. Add API credentials in Preferences to search online."* when `PlantAPIManager.configured_source_count == 0`. If one configured provider answered with zero matches while another *raised*, the result is still an honest zero result (no modal) but the status appends *"({sources} unavailable — check Preferences.)"* naming the failed provider(s) (`PlantAPIManager.last_search_failed_sources`), so an outage is not silently masked by a neighbour's empty answer. The red *"Search failed: …"* status plus the *"check your internet connection and API credentials"* message box is reserved for a genuine technical failure (every configured provider raised). (Before this, a query for a variety absent from every database — the reporter's *mahachanok* mango — produced the failure dialog with the credentials hint even though connection and credentials were fine; the same misreport class the #294 Preferences "Test" button had.) Pinned by `tests/integration/test_plant_search_zero_results.py` and `tests/unit/test_plant_api_manager_search.py`.
- **FR-PLANT-15** *(issue #170)*: On canvas drop or tool draw of a plant, look up the species in the bundled DB (`resources/data/plant_species.json`) by scientific name → common name → alias (case-insensitive). On hit, populate `metadata["plant_species"]` with the full record (pH, NPK demand, sun, water, calendar, hardiness) so the plant detail panel shows data immediately and US-12.10d soil-mismatch warnings fire automatically.
- **FR-PLANT-16** *(issue #170)*: Bundled DB ships records for **every species exposed by the gallery** (currently 118 entries: trees, shrubs, vegetables, herbs, berries, fruits, ornamentals). Every record has `ph_min`, `ph_max`, `nutrient_demand`, `n_demand`, `p_demand`, `k_demand` populated. Where the gallery's species string differs from the canonical common name (e.g. "pea" vs "Garden Pea", "apple tree" vs "Apple Tree"), records carry an optional `aliases` array. Misses fall through to the existing API search button (FR-PLANT-14).
- **FR-PLANT-17** *(issue #213)*: Assigning a database species to an **existing** generic plant — via the plant database panel (Load Custom / Create Custom) or the Plants-menu species search (`application.py`) — writes `metadata["plant_species"]` **and** resizes the drawn footprint so its **diameter equals the species' `max_spread_cm`** (the visible change the issue requires) while keeping the plant centred. The resize is **silent** in the common case; the only thing that prompts is a **manual `spacing_radius_cm` override that conflicts with the database value** — then a dialog offers **Apply database values** (default: resize the footprint and clear the override so the database cascades) or **Keep custom values** (override *and* placed footprint left untouched). The assignment is a single undoable step (`ApplySpeciesCommand`, one undo unit, dirties the document — metadata, override, and footprint radius all revert together). Species with no usable `max_spread_cm` only update metadata (no resize). The footprint is resized via `CircleItem.set_radius_centered()`, which keeps the rotation pivot on the new centre so a rotated plant does not drift on save/reload.
- **FR-PLANT-18** *(issue #297)*: Confirming a plant search result in `PlantSearchDialog` (OK or double-click) fetches the provider's full per-species detail record via `PlantAPIManager.get_by_id()` and merges it onto the search result before it is assigned to a plant. The merge is generic (`_merge_detail_into_search_result()`, a loop over every `PlantSpeciesData` field): a field at its dataclass default — or `None`, regardless of the field's own default — in the detail response defers to the search result's value; every other field takes the detail response's value. `source_id`/`data_source`/`raw_data` always come from the detail response. Search/list endpoints can be structurally sparser than detail endpoints for the same provider — confirmed live for Trefle's `/plants/search`, which omits `growth`/`specifications`/`foliage` entirely, so `sun_requirement`, `water_needs`, `ph_min`/`ph_max`, `nutrient_demand`, `foliage_color`/`foliage_texture`, and (also detail-only) `max_height_cm`, `growth_rate`, `description` would otherwise stay at their unset defaults for every Trefle-sourced plant regardless of parser correctness. The fetch runs once, on confirm, not per browsed result (rate-limit consideration); is skipped for anything that isn't a known online provider (`data_source` not in `{"trefle", "perenual", "permapeople"}`, or an empty `source_id`) -- local custom/bundled entries and unidentifiable results have no online detail endpoint to fetch. **Two failure modes, two behaviors**: a provider signaling "no richer detail exists for this record" — `PlantDetailUnavailableError`, raised for Perenual's free-tier paywall (HTTP 429, live-confirmed not rate limiting) and for Trefle records with a present-but-null `main_species` (~4% of a live sample, all scientific-name-only species) — falls back **quietly** (logged, no user-facing warning), since nothing is actually wrong. A genuine failure — a raised error, or a successful response whose `source_id` doesn't match the one requested — shows a translated warning before falling back, so a real failure can't silently reproduce #297's own symptom. Deliberately does **not** reject on an empty/missing `common_name` alone: Trefle omits it for many genuinely valid, scientific-name-only species, and a first cut of this fix wrongly discarded fully-populated detail records on that basis (caught in senior review round 2). **Enrichment gain is provider-dependent** (measured live, senior review round 7): Trefle's detail response consistently adds `description`/`sun_requirement`/`water_needs`/`ph_min`/`ph_max`/`nutrient_demand` over its search response, but Perenual's and Permapeople's detail responses did not carry any field their own search responses lacked in the sample checked — so a confirm against those two providers still requests a detail round-trip without a measured data gain in that historical sample. Acceptance now fetches details on a worker while the dialog remains responsive. Changing the selection, starting another query or closing the dialog invalidates the pending response; only enrichment for the current selection can complete acceptance. Not a bug (their parsers may grow to use more detail-only fields later), but worth knowing before assuming every provider benefits equally. **Manual-testing finding (2026-08-10)**: a result row previously showed only `"{common_name} ({scientific_name})"`, with nothing indicating which store served it. Since the custom library is searched first (FR-PLANT-14) and is not deduplicated against API results, a stale or bogus custom entry sharing a name with a real species was visually indistinguishable from -- and silently shadowed -- the live API record; confirming it skipped enrichment entirely (`data_source == "custom"`) with no explanation shown. Every result row now shows its data source (e.g. "Tomato (Solanum lycopersicum) — Custom Plant" vs "— Trefle") via the shared `plant_source_label()` helper (`ui/plant_species_assignment.py`), also used by the properties panel's own "Data Source" tooltip so the two can't drift apart. **File-size consequence, documented not fixed (final review pass, 2026-08-11)**: `raw_data` (the full provider response, kept for `"Extensible metadata for API-specific fields"` per its own field comment) is one of the three fields `_merge_detail_into_search_result()` always takes from the detail response, deliberately and pinned by `test_source_id_data_source_and_raw_data_always_come_from_detail`. Before this fix, a Trefle-sourced plant's persisted `raw_data` was the sparse search-result payload (enrichment never ran); after it, a successfully enriched plant persists the full detail response instead -- larger, but not a new category of data: every provider's `search()` result was already persisting its own raw API response the same way. No code currently reads `raw_data` back for any provider. Left as-is rather than stripped, since removing it would contradict the existing, deliberately-tested "detail's raw_data is the richer payload" invariant on a doc-and-hygiene finding -- revisit only if `.ogp` file size becomes a measured problem.

## FR-15: Soil Health Tracking (Phase 12, US-12.10)

- **FR-SOIL-01**: Per-bed soil test entry via right-click → "Add soil test…"; project-wide default via Garden → "Set default soil test…"

- **FR-SOIL-04**: Records persist in the `.ogp` file under top-level `soil_tests` and survive save/load round-trip
- **FR-SOIL-05**: Adding a record is undoable via the standard command stack and marks the project dirty
- **FR-SOIL-06** (US-12.10b): Canvas overlay tints beds by overall / pH / N / P / K health bucket; untested beds show a hatched-grey pattern

## FR-19: CAD Precision — Typed Coordinate Input + Unified Snap (Phase 13, Package A)

- **FR-INPUT-01** (US-A1): Relative coordinate input `@dx,dy` types a vertex at `(last_point.x + dx, last_point.y − dy)`. The Y-flip implements math convention (`+dy` = up on screen). Available on every multi-click drawing tool (polyline, polygon, rectangle, circle, ellipse, construction line, construction circle) via the status-bar field and the Dynamic Input overlay. Without an anchor point, relative input is rejected with an inline red error tint *and* the parser's diagnostic surfaces in the field's tooltip (e.g. "Relative input requires an existing point to anchor to"); the diagnostic clears on the next keystroke or successful commit.
- **FR-INPUT-02** (US-A2): Polar coordinate input `@dist<angle` (degrees, `0° = east`, CCW positive) types a vertex at `last_point + (dist·cos θ, −dist·sin θ)`. Polar input without a `@` prefix is also accepted and treated as relative to the last point. Polar input requires exactly one `<`. Without an active `last_point` the parser raises `ParseError` (no silent fallback to origin).
- **FR-INPUT-03** (US-A4): Dynamic Input overlay — a frameless distance/angle entry follows the cursor inside the canvas viewport. Visible only when (a) dynamic input is enabled in the View menu, (b) the active tool is not SELECT, and (c) the active tool has a `last_point` to anchor against. Tab cycles fields, Enter commits, Esc returns focus to the canvas. The overlay and the status-bar field mirror a single `CoordinateInputBuffer` per CanvasView; typing in one updates the other live.
- **FR-INPUT-04**: Smart decimal/separator handling (rules A–F in `parser.py`): `;` is always a field separator, mixed `.`/`,` resolves to `.` decimal + `,` separator, comma-only inputs disambiguate by count (1 → separator, 3 → locale decimal pair, 2 → ambiguous with locale-decimal preference and `parse_alternative()` exposing the secondary reading). Whitespace also works as a separator everywhere.
- **FR-SNAP-04** (US-A3): Midpoint snap — yields the midpoint of every straight edge from rectangles, polygons, polylines and construction lines near the cursor. Toggle in View menu → "Snap to Midpoints"; persisted via `AppSettings.midpoint_snap_enabled` (default on). Visual glyph: filled green triangle.
- **FR-SNAP-05** (US-A3): Intersection snap — computes pairwise segment-segment intersections between edges of items near the cursor, capped at 60 segments per query for predictable latency. Self-intersections within a single item are filtered out to avoid duplicating endpoint mode at polygon vertices. Toggle in View menu → "Snap to Intersections"; persisted via `AppSettings.intersection_snap_enabled` (default on). Visual glyph: green X.
- **FR-SNAP-06**: Snap engine performance — a 1000-item scene snaps under 16 ms per query (60 fps budget); enforced by `tests/unit/test_point_snapper.py::test_perf_end_to_end`. The quadtree pre-filter rebuild is guarded by a warm-up plus five repeated samples in `tests/unit/test_snap_spatial_index.py::test_perf_thousand_items`: the **median** build must be below 200 ms and the median of five 100-query batches below 1 ms. This is a shared-runner regression guard, not a claim that a single wall-clock sample is 200 ms: the historical Python 3.11/Linux single-sample outlier was 284 ms, while repeated local Python 3.12/Windows samples were approximately 15 ms. The median rejects a sustained regression while absorbing an isolated scheduler spike; the platform assumptions and evidence are recorded in ADR-020's #354 addendum.

## FR-20: CAD Precision — Curve Tools, Corner Edits, Reference-Point Snaps (Phase 13, Package B)

### FR-20.1 Curve Tools
- **FR-DRAW-08** (US-B1): Cubic Bezier pen tool. Click-drag per anchor — drag direction sets the outgoing handle; the incoming handle is mirrored automatically for a smooth tangent default. Double-click or Enter commits the curve. ESC cancels. A placed curve is reshaped in place via control handles (see FR-EDIT-12). Shortcut: `B`.
- **FR-DRAW-09** (US-B2): 3-point arc tool. Click **start → end → bulge** — the 2nd click sets the arc's end and the 3rd sets the curvature (the point the arc bulges through). The unique circular arc through the three points is computed via the circumcenter (`core/cad_geometry.arc_from_three_points`) and rendered as an `ArcItem`. (Click order chosen per manual-test feedback on #195: users fix the span first, then dial in curvature, rather than the classic start→through→end order.) The arc is rendered from exact cubic-Bézier segments (`arc_to_painter_path`), so the drawn curve terminates precisely on the user's clicks at any radius — Qt's `arcTo` could otherwise drift the rendered end by millimetres on a shallow, large-radius arc (FR-EDIT-13, ADR-025). If the three points are collinear (twice the signed triangle area ≤ 1.0), the tool falls back to a 2-vertex polyline (start→end) and a status-bar note. Shortcut: `A`.

### FR-20.2 Corner Editing
- **FR-EDIT-10** (US-B3): Fillet tool — round a polyline / polygon / rectangle corner with a tangent arc. The picked corner vertex is split into two tangent points (at distance `r/tan(α)` along each edge from the corner) and a free-standing `ArcItem` is added between them. The most-recently-used radius persists in `AppSettings.fillet_last_radius_cm`; press `R` mid-session to change it. If the radius is too large for the corner (offset > either edge length) the click is ignored with a status-bar hint. Shortcut: `Shift+F`. Filleting a rectangle is a **destructive conversion** (rect → 5-vertex polygon + arc); undo restores the rectangle (ADR-022).
- **FR-EDIT-11** (US-B3): Chamfer tool — bevel a corner with a straight cut at distance `d` along each adjacent edge. Same picking + persistence model as Fillet (`AppSettings.chamfer_last_distance_cm`, press `D` to change). No arc is created — only the host item's vertex list changes. Rectangles convert to polygons just like fillet. Shortcut: `Shift+C`.

### FR-20.3 Reference-Point Snaps
- **FR-SNAP-07** (US-B4): Nearest snap — yields the closest point on any visible edge or curve to the cursor as a fallback below all other snap modes. Priority 45 (lowest), default off (avoids surprising users who rely on free placement near edges). Toggle in View menu → "Snap to Nearest Point"; persisted via `AppSettings.nearest_snap_enabled`. Visual glyph: hourglass.
- **FR-SNAP-08** (US-B5): Perpendicular snap — drops a foot from the active tool's `last_point` onto the nearest straight edge in range. Requires a `reference_point` (no candidate without an anchor — purely cursor-based perpendicular is meaningless). Priority 25. Default off. Toggle in View menu → "Snap Perpendicular"; persisted via `AppSettings.perpendicular_snap_enabled`. Visual glyph: ⊥.
- **FR-SNAP-09** (US-B6): Tangent snap — from the active tool's `last_point` to a circle or arc, computes the contact point of the tangent line via `α = acos(r/|RC|)`. Returns the tangent point closer to the cursor when both solutions are visible. Reference points inside the circle or at the center yield no candidates. For arcs, candidates are filtered to those lying within the arc's sweep. Priority 26. Default off. Toggle in View menu → "Snap Tangent"; persisted via `AppSettings.tangent_snap_enabled`. Visual glyph: small circle + tangent line.
- **FR-SNAP-10** (issues #196/#192/#197): Snap → durable constraint. When a drawing tool commits a vertex at a snapped point, the snap becomes a geometric constraint stored on the scene's `ConstraintGraph` (via the undoable `AddConstraintCommand`): NEAREST/PERPENDICULAR on a straight edge → `POINT_ON_EDGE` (the vertex rides that named edge); MIDPOINT → `COINCIDENT` (vertex pinned to the edge midpoint); NEAREST on a circle/arc → `POINT_ON_CIRCLE`; TANGENT on a circle/arc → `POINT_ON_CIRCLE` + the new `TANGENT` constraint (TANGENT = edge⟂radius; the pair welds the contact to the rim *and* keeps the edge tangent, robustly under drag — see ADR-024). The source edge is identified by `SnapCandidate.source_edge_index` and resolved to concrete anchors by matching `get_anchor_points(source)`. Emitted constraints are enforced by the existing drag pipeline: dragging the reference item drags the constrained vertex along (`_compute_constraint_propagation`), and dragging the constrained item keeps its vertex on the edge/circle (`_enforce_point_on_edge_positions`). A perpendicular snap intentionally emits `POINT_ON_EDGE` rather than the rotation-only `PERPENDICULAR` type (see ADR-024).

### FR-20.5 Curve Editing (Package B follow-up)
- **FR-EDIT-12** (US-B9, issue #193): In-place reshape of placed Bezier and Arc curves. Selecting a curve shows draggable control handles (`CurveEditMixin` + `CurveControlHandle`); deselecting hides them. *Bezier*: an on-curve handle per anchor (drag carries both tangent handles along) plus a tangent handle for each anchor's active control point — dragging a tangent mirrors the opposite one for a smooth (C1) join, **Alt** breaks it into a corner; endpoint anchors expose only their single live handle. *Arc*: start / through / end handles (any drag recomputes the 3-point arc, so the through-point changes curvature with endpoints fixed) plus a read-only centre marker; a drag that would make the points collinear is rejected. Each drag commits exactly one undo step (`SetCurveGeometryCommand`, geometry-snapshot). The arc persists its through-point (additive `through_x`/`through_y`; legacy files derive the angular midpoint) so handles round-trip through save/reload. Reshape only — adding/deleting anchors or arc control points is out of scope. (ADR-025.)
- **FR-EDIT-13** (US-B11, issue #195): 3-point arc endpoint precision — the rendered arc must terminate on the user's clicks within 1e-3 cm at any radius/sweep. Implemented by rendering arcs from exact cubic-Bézier segments rather than Qt's `arcMoveTo`/`arcTo` (see FR-DRAW-09, ADR-025). The fillet arc inherits the same precise rendering.
- **FR-EDIT-14** (US-B4, issue #187): Mirror tool — reflect the selected shapes across a user-defined axis. Workflow: select shapes → `Shift+M` → click axis start → click axis end (**Shift** constrains the axis to 0/45/90°) → a small modal asks **Copy** (default) or **Move**. *Copy* adds reflected duplicates (fresh ids, so — like paste — copies start unconstrained) and keeps the originals; *Move* replaces the originals with reflections that keep their `item_id`, so existing constraints stay bound. Selecting a bed auto-includes its plants so they reflect with the bed. The reflected result is clamped back onto the canvas (shifted as a group) if the axis would push it off-bounds. One undo step per mirror (`MirrorItemsCommand`). Supported types: polyline, polygon, rectangle, ellipse, circle, arc, bezier — plus rectangle/circle-based SVG furniture & plants, which reflect *positionally* and render un-flipped (LibreCAD behaviour). Text, callouts, journal pins, construction geometry, background image, and groups are skipped with a status note. Geometry is reflected by rebuilding each item (not a Qt mirror transform), so results round-trip through save/load and DXF. Distinct from the Symmetry *constraint* (`CONSTRAINT_SYMMETRY`), which is a persistent relationship rather than a one-shot copy. (`core/mirror_geometry.py`, ADR-026.)

## FR-22: Sidebar Accordion — Hover-Peek + Click-to-Toggle (issue #226, ADR-030)

## FR-26: Agent API — Embedded MCP Server (Phase 13, Package D, US-D1.1, epic #237)

> **Scope:** US-D1.1–D1.6 ship the embedded server, read/query/vision/export surfaces, resources/prompts, and client onboarding. D2.0–D2.6 add the token-gated write surface (creation, domain and low-level geometry edits, species/bed links, layers, and global undo/redo); D3 remains follow-on work. See ADR-033, ADR-034, ADR-035, ADR-036, §8.19.

- **FR-AGENT-01**: The app can host an **MCP server over streamable-HTTP** for AI agents (Claude, Cursor, any MCP client), embedded in the running GUI on a background thread and reachable at `http://127.0.0.1:<port>/mcp`.
- **FR-AGENT-02**: The server is **on by default** (read-only) so AI assistants can connect without users hunting through Preferences. A Preferences → **Agent API** group (Enable checkbox + Port spin-box 1024–65535 + read-only connect-URL label) persists in `AppSettings` (`agent_api/enabled` default **on**, `agent_api/port` default **8765**); it **auto-starts on every launch** and users can disable it there.
- **FR-AGENT-03**: The server binds **127.0.0.1 only** (never the LAN). Read tools use the D1 loopback-trust model; every scene-mutating D2 tool, including global `undo`/`redo`, is additionally gated by the writes-enabled setting and the bearer token defined in FR-AGENT-13/ADR-036. A port already in use is reported in the status bar without crashing.
- **FR-AGENT-04**: Tool **`get_plan_summary`** returns a curated, stable summary of the open plan: bed/plant/other-shape counts, canvas size (cm), layer names, file name, and unsaved-changes flag. Reading the plan never mutates it.
- **FR-AGENT-05**: Agent reads and D2+ edits are marshaled onto the Qt main thread; the server stops cleanly when the toggle is turned off and on app close. Tool/resource/prompt descriptions are an English API contract (exempt from i18n); only the Settings UI strings are translated.

**US-D1.2 — read/query tools** (additive; no `FILE_VERSION` change):

- **FR-AGENT-06**: **`list_objects(type?, layer?, parent?, raw?)`** enumerates top-level objects; **`get_object(item_id, raw?)`** returns one object's full detail. Objects are addressed by stable UUID; `type` accepts an `ObjectType` name, a category (`bed`/`plant`/`shape`), or a geometry kind. Both return the curated schema (`ObjectRef`/`ObjectDetail`), or the raw serialiser dict(s) when `raw=true`.
- **FR-AGENT-07**: Spatial tools locate and measure objects in scene centimetres: **`objects_in_region(x, y, width, height)`** (bounding-box intersection), **`objects_in(parent_id)`** / **`plants_in_bed(bed_id)`** (container contents), **`nearest_objects(x, y, k?, type?)`**, and **`measure_distance(id_a, id_b)`** (centre-to-centre). Coordinates are the native scene frame (CAD Y-up per ADR-002: origin bottom-left, +x east/right, +y north/up — a larger y is further north); non-rectangular shapes use their bounding box.
- **FR-AGENT-08**: **`get_diagnostics(kind?)`** reports the plan's current warnings — companion conflicts, spacing overlaps, soil/pH mismatches, container capacity overruns, and crop-rotation conflicts — by reading the **already-computed** flags the canvas shows as badges (no recomputation). Positive indicators are not reported.

**US-D1.3 — vision tool** (additive; no `FILE_VERSION` change):

- **FR-AGENT-09**: **`render_canvas_image(x?, y?, width?, height?, layers?, image_width_px?)`** returns a PNG screenshot of the live canvas (a region in scene cm, or the full canvas by default) plus a structured `RenderMeta` block (rendered region, output pixel size, `px_per_cm`, layers actually shown). `layers` is an optional layer-name allowlist (unknown names match nothing, not an error) that **overrides** what's currently shown — a layer the user has toggled off in the live Layers panel is rendered anyway if requested, and every layer's visibility is restored to its prior state afterward. Output width is clamped to 128–2048px (default 1024), with the derived height independently clamped to the same bounds. Selection handles and construction geometry are never shown. The image's pixel Y-axis is inverted relative to the native scene frame (FR-AGENT-07) — `RenderMeta.px_per_cm`'s description documents the exact correction formula. Reading/rendering the plan never mutates it or the user's live selection.

**US-D1.4 — export/save tools** (additive; no `FILE_VERSION` change):

- **FR-AGENT-10**: **`save_plan(file_path?)`**, **`export_pdf(file_path?, paper_size?, orientation?)`**, **`export_dxf(file_path?)`**, and **`export_csv(kind, file_path?)`** write a file to disk via the same services the GUI's File > Export/Save menu uses — the PDF report, a DXF drawing, or a CSV (`kind` = `'shopping_list'` or `'harvest'`), and the project's own `.ogp`. None of these mutate the in-memory plan except `save_plan`, which persists what's already on screen (mirroring the GUI's save path exactly, including its stale-shopping-list-price cleanup) — no token auth is required (reserved for D2's scene-mutating write tools). Omitting `file_path` writes to a sensible default next to the currently open project (or the app's Documents folder); `save_plan` with no project open and no `file_path` raises rather than inventing a filename, mirroring the GUI's own Save-As requirement for a brand-new project. Given an explicit `file_path`, the destination's parent directory must already exist, and — unlike a `QFileDialog` save prompt — an unrelated existing file at that path is overwritten without confirmation. All four return a shared `ExportResult` (written path, format, row count for CSV, and — for `save_plan` — the project's prior file path if the call redirected it).

**US-D1.5 — resources + read-analysis prompts** (additive; no `FILE_VERSION` change):

- **FR-AGENT-11**: Five read-only MCP **resources**: **`garden://plan`** (curated `PlanSummary` — same data as `get_plan_summary`), **`garden://plan/raw`** (the uncurated snapshot dict), **`garden://canvas.png`** (a PNG of the full live canvas, no region/layer args — same pipeline as `render_canvas_image`), **`garden://diagnostics`** (same data as `get_diagnostics`), and **`garden://species`** (the bundled species database — 118 records, static data with no `AgentProviders` field or main-thread hop, since `services/bundled_species_db.py` has no Qt dependency). Two read-analysis **prompts**: **`audit-plan`** (plan summary + current diagnostics, asks for prioritized improvement suggestions) and **`describe-garden`** (plan summary + object list, asks for a narrative description) — both compose live data via a new Qt-free `agent_api/prompts.py`, no write/guided-edit prompts (deferred to D3). Verified directly against the installed `mcp==1.28.1` source: resource functions returning `bytes` with an explicit `mime_type` produce a base64-encoded `BlobResourceContents` automatically (no `Image`/`structured_output=False` workaround, which is tool-only), and non-`str`/`bytes` returns (a pydantic model, a `dict`, a `list`) auto-serialize to JSON text via `pydantic_core.to_json`.

**US-D1.6 — AI client onboarding** (additive; no `FILE_VERSION` change):

- **FR-AGENT-12**: A discoverable **"Connect AI Assistant…"** entry point (Help menu, and a matching button in Preferences → Agent API) opens a dialog showing the connect URL (Copy button) and the transport (Streamable HTTP). The dialog **detects** installed AI clients by their known config locations — **Cursor** (`~/.cursor`), **Claude Code** (`claude` CLI on `PATH` or `~/.claude.json`), **Claude Desktop** (the platform app-data folder) — and offers **one-click registration** where each client's own documented mechanism supports a safe automatic path: a direct JSON merge into `~/.cursor/mcp.json` for Cursor, and for Claude Code the `claude mcp add --transport http --scope user` CLI when it's on `PATH` — **and, when it isn't, a direct atomic merge into `~/.claude.json`'s top-level `mcpServers`** (the same user-scope `type: "http"` entry the CLI writes, read by both the CLI and the VS Code extension), so a machine without the CLI still gets a working one-click. **Claude Desktop is detection-only and cannot reach a localhost server at all** — its connectors are reached from Anthropic's cloud and reject `localhost`/`http://` URLs — so its row shows an honest "use Claude Code or Cursor instead" note, with no button and no snippet. Every client with an automatic path also gets a copy-paste JSON snippet with a short "where to put this" note. Automatic writes preserve every other key/server in the target file, back up its current contents before touching it (a second run's backup reflects the most recent pre-write state, not the pristine original), and write atomically (temp file + rename) — never clobbering existing configuration. The connect URL always comes from asking whether the server is actually running, never reconstructed from settings — a saved port can still be dead (e.g. a port conflict at launch). The merge into `~/.claude.json` (which also holds OAuth tokens and project trust) fails **closed** — an unreadable file is left byte-for-byte untouched rather than replaced. The dialog's client rows sit in a scroll area, so revealing a manual snippet scrolls it into view instead of clipping it behind the Close button. No token auth is needed (registering a client isn't a scene-mutating action). See ADR-035 (and its issue-#253 addendum).
- **FR-AGENT-13** (US-D2.0, the first agent **write** tools): with **"Allow AI assistants to edit the plan"** enabled in Preferences → Agent API (**off by default**), the server exposes two scene-mutating tools — **`move_object(item_id, dx, dy)`** (move by a relative offset in scene cm; the canvas is Y-up per ADR-002, so a positive dy moves the object north and a negative dy south — the same frame the read tools report; a bed/container/trellis carries its contained plants along, and a moved plant has its bed membership re-evaluated afterward, mirroring the GUI's own drag-release behaviour) and **`delete_object(item_id)`** (detaches contained plants, removes any constraint referencing the object, and deletes a `HOUSE`'s linked roof ridge — all matching the GUI's own delete orchestration, not just its `DeleteItemsCommand`) — each requiring a bearer token and each applied via the same `command_manager.execute` path the GUI uses (Ctrl+Z reverses it, and it marks the plan dirty). `delete_object` is one undo step; `move_object` is one step for a lone item and two when the move also reparents a plant across a bed boundary — never more. Both tools **refuse** (raise a clear error) rather than silently mishandle cases outside their supported contract: an object participating in a geometric constraint (per the final D2.6 contract, agent geometry writes permanently refuse rather than silently skipping `CanvasView`'s multi-item live solver; `get_geometry` exposes the blocking constraint), a journal pin (its delete needs a `ProjectData` note-record prune a bare `DeleteItemsCommand` doesn't do), an object on a **locked layer** (the GUI makes locked-layer items entirely non-interactive; the agent must honour that protection too), and an individual **group member** (the GUI only ever moves/deletes the whole group — address the group by its own id). **Write tools are gated two ways**: they are registered only when editing is enabled **and** a token is configured (otherwise they don't appear in the tool list at all), and every call must present the token — **either in the server URL as a `?token=` query parameter (the reliable route: some clients, notably Claude Code on streamable-HTTP, store a configured header but don't send it on tool-call requests) or as an `Authorization: Bearer <token>` header** — an unauthenticated or wrong-token call fails and leaves the scene untouched. Reads remain open (loopback trust, unchanged), so this doesn't affect clients that only read. The token is **auto-generated** (shown with Copy/Regenerate in Preferences, and injected into each client's config by the "Connect AI Assistant" dialog as a `?token=` on the connect URL); regenerating it revokes prior clients. Delivering the secret in the URL means it can appear in local request logs — an accepted, loopback-only exposure (the same secret already lives in the client's config). No `FILE_VERSION` change. See ADR-036. Later D2 stories add create/resize/rotate/species/reparent/layer tools behind the same gate; D3 adds domain-intelligence + guided-edit prompts.
- **FR-AGENT-14** (US-D2.1, agent **object creation**): behind the same two gates as FR-AGENT-13 (editing enabled **and** a valid token), the server exposes **`create_object(object_type, x, y, width?, height?, radius?, name?, species?)`**, which adds one new object to the plan. Scope for this slice is **plants + soil containers**: the round types **TREE**, **SHRUB**, **PERENNIAL** (radius optional — omitting it uses the app's own gallery-drop defaults of 100/50/30 cm) and **CONTAINER_ROUND** (radius required — a pot has no house default), plus the rectangular **GARDEN_BED**, **RAISED_BED**, **CONTAINER** and **WALL_PLANTER** (both `width` and `height` required). `x`/`y` are the object's **centre**, in the same Y-up scene frame the read tools report (a larger y is further north), so an agent can place an object relative to one it just read without converting anything; the centre→anchor conversion for rectangles is `anchor = centre − extent/2`, which holds in either y-direction reading and so cannot introduce a Y-flip error. The item itself is built by **`ProjectManager._deserialize_item_core`** — the `.ogp` loader's own factory — so an agent-created object is constructed by exactly the code path a loaded one is, adding no second item-construction path to drift. The tool mirrors the GUI's gallery-drop orchestration rather than just `CreateItemCommand` (with one deliberate omission: the drop handler also sets `plant_category` from the gallery's drag payload, which `create_object` does not expose — the SVG resolver's species tier covers the useful case, and the category tier is simply unreachable for agent-created plants): a `species` matching the bundled database is **auto-populated** into the item's species metadata (so the plant-detail panel and FR-SOIL mismatch warnings light up without a manual search), **every** new plant is stamped with today's **planting date** — deliberately whether or not a species was given, since a placeholder that gains a species later must not be left permanently undated for the growth/shadow/heatmap/3D views (FR-SUN-08) — and the object lands on the **currently active layer** (or on no layer at all when the scene has none active — matching the GUI drop path). Two asymmetries are stated rather than hidden: a **locked** active layer is refused, but a **hidden** one is silently un-hidden by `QGraphicsScene.addItem` (as it is for the GUI's own draw tools) and **undo does not re-hide it**, so that one visibility change sits outside the undo step. A plant created inside a bed is linked to that bed **within the single create step** (`CreateItemCommand.execute` already calls `_auto_parent_plant`, and its `undo` calls `_detach_from_parent`), so unlike `move_object` this is **always exactly one undo step**; the resulting parent is reported as `new_parent_bed_id` while `bed_membership_changed` stays false (it denotes a *second* undo step, which create never produces). The tool **refuses** (raises a clear error naming every supported type) rather than guessing: an object type outside the slice, a dimension that doesn't fit the type's shape (`width` on a round type, `radius` on a rectangular one), a missing required dimension, a zero/negative extent, a non-finite (NaN/infinity) coordinate or extent, a **species on a non-plant type** (the only silent-ignore an otherwise loud tool would have had), an **implausibly large extent** (capped at twice the plan's larger canvas dimension, and additionally at 5000 cm for a plant, whose footprint drives a quadratic main-thread `QImage` allocation sized in scene centimetres — the shape of a metres-for-centimetres unit slip), a **position further than one canvas beyond an edge** (unreachable by any GUI gesture), and a **locked active layer** — the GUI cannot draw onto a locked layer either. Every refusal leaves the scene and the undo stack untouched. Parameter validation lives in the Qt-free `agent_api/creates.py`, whose object-type name sets carry drift guards against the real `ObjectType` definitions. No `FILE_VERSION` change. See ADR-036 (US-D2.1 addendum).
- **FR-AGENT-15** (US-D2.2, agent **resize + rotate**): behind the same two gates as FR-AGENT-13 (editing enabled **and** a valid token), the server exposes **`resize_object(item_id, width?, height?, radius?)`** and **`rotate_object(item_id, angle, relative?)`**, completing core single-object manipulation (create / move / delete / resize / rotate). Dimensions are **absolute targets in centimetres**, the same vocabulary `create_object` uses — `radius` for round objects, `width` and/or `height` for rectangular ones, either axis alone leaving the other unchanged. **The object's scene centre is preserved for every type**, so the coordinates an agent read before the resize remain valid afterwards; the resulting centre is echoed back from the same source the read tools use. `rotate_object` takes **degrees, positive = counter-clockwise** — an object whose long axis points east points north after `+90`; this convention was determined by measuring a real item rather than assumed, and is pinned in two test suites against a corner position before and after (never against the stored angle), because issue #267 is what a docstring stating a frame the code doesn't honour costs. Rotation is **absolute by default** (calling it twice with 90 leaves the object at 90) with `relative=True` to accumulate; the result is normalised into `[0, 360)` and reported as `rotation_deg`. Both tools apply exactly **one undoable step** — neither reparents, so unlike `move_object` neither can produce a second — and both route through **`ui/canvas/geometry_apply.py`**, the canonical geometry-apply path this story extracted so that every rect-backed caller shares one function instead of one closure apiece (`apply_rotation` now has exactly one definition in the codebase; the authoritative list of callers and the two deliberate exceptions is that module's own docstring, stated there only). That extraction also **fixed three live GUI bugs it exposed, none of them introduced by this story** — all exactly 0 at rotation 0, which is why none had ever been reported: the properties panel's numeric resize displaced a rotated object by **73.2 cm** (30° / 50→100 cm); the vertex-edit corner drag left the stored centre **331 cm** from the visible one; and the EQUAL-constraint partner resize moved a size-linked rotated partner by **70.7 cm** at 90°. The tools **refuse** (raise a clear error, leaving the scene and undo stack untouched) rather than guessing: a **vertex-backed** object (polygon/polyline — refused by name, with vertex editing deferred to a later slice), a dimension that doesn't fit the object's shape, no dimension at all, a zero/negative/non-finite extent, an extent below the 1 cm floor the GUI itself enforces or above D2.1's canvas-relative cap (plus the plant-diameter cap), a non-finite or implausibly large angle, an object participating in a **geometric constraint** (the live constraint solver has no one-shot equivalent, so editing would silently violate the constraint), and — through the write path's shared resolver — a journal pin, a group member, or an object on a **locked layer**. Validation lives in the Qt-free `agent_api/edits.py`. No `FILE_VERSION` change. See ADR-036 (US-D2.2 addendum).
- **FR-AGENT-16** (US-D2.3, agent **species assignment + explicit bed reparenting**): behind the same two gates, the server exposes **`set_species(item_id, species?, apply_database_size?)`** and **`set_parent_bed(item_id, bed_id?)`**, closing two gaps that only existed for objects that *already* exist. `set_species` gives a plant the user drew by hand a species — resolved against the **bundled database** by scientific name, common name or alias through the same resolver `create_object` uses — which is what makes the plant-detail panel, the planting calendar and the FR-SOIL mismatch warnings apply to it; `species=null` clears it. Assignment goes through **`ui/plant_species_assignment.apply_species_to_item`**, the helper issue #213 extracted so the plant-database panel and the species search cannot diverge, making the agent a third caller rather than a third implementation. As in the app, the drawn footprint adopts the species' real mature size (diameter = `max_spread_cm`); **`apply_database_size` (default `true`) is the agent's answer to the two-button dialog the GUI shows when a manual `spacing_radius_cm` override disagrees with the database** — `true` takes the database values and clears the override, `false` keeps the user's — and is **not** a general "don't resize" switch, since without a conflicting override the footprint adopts the database size either way. The deliberate asymmetry with `create_object` (which sizes a new plant from the gallery defaults, because `radius` is an explicit creation parameter that a species must not silently overrule) is documented rather than reconciled: an agent wanting a database-sized new plant calls `create_object` then `set_species`. `set_parent_bed` links a plant to a bed or detaches it (`bed_id=null`) as a **link change only — the plant does not move**, reaching the one state `move_object` cannot: a plant already sitting inside a bed drawn around it and therefore never linked. It **deliberately does not require geometric containment** (the app's own Link action does not either, and requiring it would defeat the tool's purpose); the result's `link_is_geometric` reports whether the link and the geometry agree. It is the application's own link test — the centre of the plant's bounding box against the bed's outline — and a warning badge on the plant moves that point by 1.8 cm along each axis (about 2.5 cm diagonally), so within that margin of a bed's edge it can read `false` for a plant that the sun study and the Living Garden 3D scene do stand on the bed's soil (FR-SUN-11 tests the plant's own centre), and `true` for one they leave on the ground. The field's description in the tool schema says so, in the words an agent reads. A plant's parent may be any soil container **or a `TRELLIS`** — which holds plants but has no soil, per §8.14/ADR-017 — and anything else is refused by name with the valid options listed. Undo restores the plant's **original** z-value rather than a recomputed one, and soil-mismatch diagnostics are refreshed explicitly because parent-link mutations don't fire `QGraphicsScene.changed`. Because assigning a species resizes the footprint, `set_species` is a geometry mutation and **refuses a constrained object** exactly as `resize_object` does — otherwise an agent blocked by one tool could obtain the same resize through the other; clearing a species resizes nothing and is not gated. Both tools apply exactly **one undoable step**; both **refuse** (leaving scene and undo stack untouched) on a non-plant object, an unknown species name, a target that cannot hold plants, a **no-op** (linking a plant to the bed it is already in, or clearing a species that was never set), a journal pin, a group member, or a **locked layer**. `WriteResult` gains `species_key` and `link_is_geometric`. No `FILE_VERSION` change. See ADR-036 (US-D2.3 addendum).

## FR-27: Sun/Shade Foundation — Solar Engine + Object Heights (Phase 14, US-E1+E2, epic #255)
**US-E1 — solar position engine** (no UI; no `FILE_VERSION` change):

- **FR-SUN-01**: The application computes the sun's position (geometric + refraction-corrected elevation, compass azimuth clockwise from true north, declination, equation of time, hour angle) for any site latitude/longitude (+east) and any timezone-aware UTC instant, to within ±0.5° (NOAA/Meeus formulation, actual accuracy ±0.1° class for 1900–2100). Naive datetimes are rejected with a clear error. Exclusions (stated, Phase 14): downstream shadow features use the *geometric* elevation (refraction ≤0.02° above 30° elevation is irrelevant at garden scale); site `elevation_m` does not shift on-site shadows; terrain slopes are out of scope.

**US-E2 — object height property** (additive `metadata["object_height_cm"]`; no `FILE_VERSION` change — old app versions preserve the key untouched):

- **FR-SUN-02**: Every height-bearing object resolves an **effective above-ground height** with the precedence: explicit user-set height → container fill height (`container_height_cm`, never aliased — it keeps meaning soil fill) → assigned species' `max_height_cm` → a per-type default (fence 120 cm, wall 200, hedge 150, house 450, garage/tool shed 250, greenhouse 220, trellis 180, raised bed 40, tables 75, chairs/benches 85, lounger 80, BBQ 90, compost bin 100) → none (object casts no shadow). The properties panel shows an **"Object height:"** field for height-bearing types (defaults-table types, containers, plants — including species-less placeholders): it displays the resolved effective height with a tooltip naming its source ("Custom height" / "From container fill height" / "From assigned species" / "Default for this object type"); typing a value stores an explicit override, setting **0 ("Auto")** clears it back to automatic. Each edit is **one undoable step** and marks the plan dirty.

**US-E3 — 2D analytic shadow overlay + sun date/time control** (runtime-only; nothing serialized; no `FILE_VERSION` change):

- **FR-SUN-03**: With the permanent solar simulation (separate from decorative drop shadows), the canvas shows a semi-transparent overlay of the unioned ground shadows of every visible object with an effective height (FR-SUN-02), computed analytically (`L = h / tan α`, footprint swept opposite the sun's azimuth) for the simulated instant and the project's garden location. Shadows recompute automatically (debounced) when items move/resize/rotate, heights change, the sim time changes, or the location changes — never during painting. The overlay renders above the background image and below all garden items, appears in PNG/PDF exports while enabled, and is never written to the `.ogp`; it is clipped to the canvas bounds (cut off at the garden edge, never spilling onto the grey area outside) and drawn with a soft feathered edge. Empty states: no garden location → overlay off with a hint naming File → Set Garden Location; sun below 0.5° geometric elevation → the whole canvas is shaded (night) with a "night" hint. Exclusions (stated, Phase 14): flat ground (site elevation and terrain slopes ignored), geometric (unrefracted) sun elevation, opaque objects only (no canopy translucency). A plant that stands on raised soil casts from that soil, not from the ground: **FR-SUN-11**.
- **FR-SUN-04**: The permanent combined Plan & Sun toolbar provides one calendar, monthly scrubber, Today, a Past/Today/Future indicator, editable time, a time-of-day slider (1-minute steps, system local timezone), and an **Animate** toggle that advances the time slider automatically (10 sim-minutes per 200 ms tick, wrapping at midnight). Solar simulation is always active and defaults to the current date and time on each app start — the sim instant is not persisted across sessions, so a fresh run always reflects today. **One simulation clock** (Phase 17 L1.0, ADR-053) holds the chosen moment for the whole app. The shadow overlay (FR-SUN-03), the hours-of-sun heatmap (FR-SUN-05) and the 3D view (FR-SUN-06) all read the same **plan date** — the local calendar day the toolbar shows, which also drives growth (FR-SUN-08) — and the same instant for the sun position. A time-of-day change (dragging the slider, animating, or wrapping past midnight, which stays on the same date) never counts as a date change: it moves the sun, keeps a computed heatmap, and does not rebuild the 3D geometry. The date picker accepts 1971-01-01 to 2999-12-31, the range the system timezone converts on every platform. Around a DST changeover the slider's wall clock always means the first occurrence: in the skipped spring hour it shows the sun of the hour after it, and the repeated autumn hour shows its first occurrence (a session started during the second one steps the sun back about an hour on the next slider move); the date never changes.

**US-E4 — hours-of-sun heatmap** (runtime-only overlay; no `FILE_VERSION` change):

- **FR-SUN-05**: An **"Hours of Sun"** button on the simulation toolbar enables automatic background updates of a full-day direct-sun heatmap for the shown date: the daylight period is sampled every 15 minutes (UTC civil day), each sample's shadow union (FR-SUN-03 machinery) is rasterized over a 10 cm grid covering the canvas, and per-cell sun minutes are rendered as a **smooth continuous cool→warm surface** (darker = fewer sun hours, fading to nearly transparent in full sun) overlaid with **topographic contour lines every hour, labeled on even hours (2 h / 4 h / 6 h…)** — the labels are the key, so no separate legend is shown. The horticultural bands (deep shade <2 h, light shade 2–4 h, partial sun 4–6 h, full sun ≥6 h) remain the domain classification the even-hour contours align with. The computation runs in a worker thread — the UI stays responsive throughout — with a dated Updating indication and an operable Off button. The overlay renders above the shadow overlay's z-order, appears in exports while shown, and is never written to the `.ogp`. While checked, date and exposure-input edits refresh automatically; an old map stays labelled with its actual date and Updating until replaced. Superseded results never become current measurements. Time-only animation preserves the full-day map. Unchecking clears it; document/location/grid changes discard old imagery. Visual exports wait for current exposure with cancellation and a 30-second deadline (ADR-062). Empty states and exclusions follow FR-SUN-03 (no location → hint; flat ground; geometric elevation clamped to ≥0.5° for grazing dawn/dusk samples). Season analysis = run the map for representative dates (equinoxes/solstices) via the date picker; no multi-date averaging in Phase 14 (stated exclusion). Plants on raised soil cast from their soil here exactly as in the overlay (**FR-SUN-11**): both use the same casters.

**US-E6 — the 3D view** (since Phase 17 L1.9 the 3D pane of the main window's workspace, engine Qt Quick 3D per ADR-048 / ADR-060; the US-E6 viewer window on Qt 3D, ADR-038, is retired; no `FILE_VERSION` change):

- **FR-SUN-06**: **View → "3D View"** shows the plan in 3D inside the main window: from Plan mode it switches the workspace to **Split** — the plan and the 3D view side by side — and in 3D or Split mode it changes nothing (the workspace's own modes Plan / 3D / Split, Alt+1 / Alt+2 / Alt+3, are FR-3D-WS-01; no separate window opens). Every visible object with a footprint stands at its **effective height** (FR-SUN-02) on the same footprint the 2D shadow overlay uses — a building with its roof, a fence with its posts and pickets, a wall, a bed, a hedge as built shapes, a plant as the silhouette of its sprite's archetype (FR-3D-PLANT-01…04), anything else as a prism in its fill colour; objects without a height (lawns, paths, in-ground beds …) lie on the ground as on the plan (the ground bake, FR-3D-GROUND-*) — on a ground the size of the canvas, in a meadow. The camera orbits (FR-3D-WS-06) and starts framed on the plan. The light is the plan's sun — location, date and time of the one simulation clock (FR-SUN-04) — with shadows whose ground coverage matches the 2D overlay's (FR-3D-LOOK-01, FR-3D-LOOK-06); without a garden location a fixed southern midday sun (50° high, azimuth 180°) lights it, and after sunset the view fades through twilight into a moonlit night. The view follows **every** edit of the plan at once (FR-3D-WS-03) — there is no Refresh — and a date change regrows the dated plants (FR-SUN-08). It is a viewer: a click selects (FR-3D-SELECT-01…05), nothing is edited in 3D, and nothing 3D is written to the `.ogp` (camera, mode and walk state are not saved with the plan; the Split position is a window setting). Detail: FR-33.

**US-E7 — first-person walkthrough** (a camera mode of the 3D view — since Phase 17 L1.9 the workspace's, FR-3D-WALK-01…03; no `FILE_VERSION` change):

- **FR-SUN-07**: **"Walk"** in the 3D pane puts the user into the garden at **eye height** — 165 cm by default; the arrow beside the button offers 150 cm and 110 cm — where the view was looking. **W A S D / the arrow keys** walk (Shift runs), **dragging the mouse** looks around, **Escape** (or the Walk button) returns to orbit with the previous orbit view restored exactly. The walker cannot leave the plan and cannot leave its eye height (no flying, no crouching), and it has a body: walls, fences, buildings, hedges, raised beds and containers stop it (FR-3D-WALK-02; plants and furniture do not). The sun and the simulation's date and time stay live while walking. Flat ground only (terrain is a Phase 14 exclusion); nothing of walking is written to the `.ogp`. Detail: FR-3D-WALK-01…03.

**US-E8 — plant growth over time** (one model, display-only; no `FILE_VERSION` change):

- **FR-SUN-08**: A plant's **measured current size** — the existing Plant Details **Current height** / **Current spread** fields — is what the sun/shade features use: its shadow (US-E3), hours-of-sun contribution (US-E4) and 3D model (US-E6, FR-3D-PLANT-02) all follow the measured height and canopy instead of the species' mature maximum. Both fields are read as literal centimetres — a 150 cm spread casts a 150 cm-wide canopy shadow, and (since issue #299) the SAME measured size drives the SVG icon's rendered size on the 2D canvas too, so a young plant now visibly looks smaller than its assigned species' mature footprint there as well. The drawn circle's own *geometry* (`rect()`/`radius` — the spacing footprint used for overlap/companion-distance diagnostics) is unaffected and stays on the mature `max_spread_cm` regardless: shrinking it to a sapling's current canopy would let the user plant too densely, so "how much room to reserve" and "how big it currently looks" are two independent things on the same item. A plant measured *beyond* its species maximum keeps its measurement rather than being clamped down to the book value. Measuring **one** dimension implies the other proportionally (a plant measured at a quarter of its mature height is treated as a quarter as wide), so a half-measured plant never renders as a pole or a pancake. The 2D shadow overlay and the 3D view (since Phase 17 L1.9, FR-3D-WS-03) follow the fields live as they are edited; while Hours of Sun is enabled, edits request a debounced refresh and the previous map remains labelled with its actual date until the new result arrives (ADR-062). Given a **planting date** as well (defaulted to the active plan date for every newly placed plant, and editable afterwards), the plant additionally **grows over time**: scrubbing the sim date forward interpolates it linearly from its current size at the planting date up to the species maximum at maturity (years-to-maturity = species `days_to_maturity` when present, else tree 10 y / others 3 y / annuals ≈ a season), consistently across the 2D sprite, shadows, heatmap and 3D from one model and one plan date (the toolbar's local day, FR-SUN-04 — before Phase 17 L1.0 the shadows and 3D used the instant's UTC date, a day off the heatmap's near local midnight). An explicit object-height override always wins. A plant the user has **not** measured keeps the mature size at every date (growth simply stays disengaged) — nothing changes for existing plans. Scrubbing the sun timeline NEVER mutates stored geometry (the drawn footprint's `rect()`/`radius` stay the mature canopy; save files are byte-identical) and the 2D sprite renders its date-projected size from that same plan date. Editing Current height/spread also changes its rendered appearance live. The underlying item geometry remains untouched, so selection/snap/`mapToScene` behave as before. While the date keeps changing — an arrow key held in the date field — the 3D view regrows its dated plants at most twice a second (the first and the last date at once) while the light follows every step (Phase 17 L1.9, #531). **Stated exclusions**: linear growth only (no sigmoid/dormancy/pruning), no separate growth toggle (the sim timeline is the growth timeline).

**Phase 17 L1.6 — plants stand on their bed** (changes the shadows of FR-SUN-03 / FR-SUN-05 for plants that are linked to and stand inside a parent with raised soil; nothing serialized; no `FILE_VERSION` change):

- **FR-SUN-11**: A plant stands on a parent's **soil** when both hold: it is **linked** to that parent (the bed membership the Properties panel shows) and its **centre lies inside the parent's shape** — the centre of the plant's circle itself, which does not move when a warning badge or a highlight is drawn over the plant; the parent is a **raised bed, container, round container or wall planter**, or a garden bed that carries a height. The link alone is not enough: the application sets it when a plant is created (placed, created in bulk, or pasted), when a selected plant is dropped after a drag, and when an agent moves a plant, and does not re-evaluate it when a bed is resized, so a plant whose bed was resized away from it — or which was linked by hand to a bed it is not in — stands on the ground, exactly as before this requirement. **Where the soil is**: in a **bed**, 2 cm below the rim (the bed's height, FR-SUN-02) — an assumption of the model, since the plan holds no fill level for a bed; in a **container**, AT its resolved height, because that height is its soil fill height (FR-SUN-02: `container_height_cm` means soil fill and stands in for the above-ground height — the plan holds no separate rim, and none is invented). The plant's own height (FR-SUN-02, FR-SUN-08) is measured from the soil: a 60 cm perennial in a 40 cm raised bed occupies 38–98 cm above the ground, in a 30 cm pot 30–90 cm. The shadow overlay (FR-SUN-03) and the hours-of-sun map (FR-SUN-05) cast it from that height: its shadow starts `base / tan α` from its footprint and its tip lies `base / tan α` further from the sun than before (`α` = solar elevation) — for the raised-bed example 54 cm further at a 35° sun and 142 cm further at 15°. The ground between the plant and the start of its shadow is shaded by the bed, which casts its own shadow as before. **What the user sees change**: before, such a plant cast as if it grew out of the ground *through* its bed, so in the middle of a bed its shadow never left the bed's own and it did not show in the shadow map at all; now the plant's shadow reaches out of the bed's, and the hours-of-sun map counts the shade it casts beyond the bed. Unchanged: every object on the ground, every plant in an in-ground garden bed (no height) or on a trellis (a plant parent that holds no soil), and every plant without a parent. A parent on a hidden layer counts as absent (its plants cast from the ground, like the parent's own shadow disappears). Raising or lowering the bed, resizing it or moving the plant updates the plant's shadow with the next recompute: **where a linked plant stands follows its centre**, whatever moved it — outside its bed's shape it stands on the ground, back inside it stands on the soil again. Only the LINK is limited (the bed-membership follow-up): it is made or removed from geometry when a plant is placed, created in bulk or pasted, when a mouse drag of the plant is released, and when an agent moves it (`move_object`, `set_object_position`). The arrow keys, a coordinate typed into the Properties panel, align / distribute and the mirror tool's Move leave the link as it was; an array copy takes its source's link as it is, and a mirrored copy made without its bed gets none. So a plant that is in a raised bed without a link to it — moved or mirror-copied in that way, or there before the bed was drawn — stays on the ground. The same rule places the plant in the Living Garden 3D scene data (Phase 17), so the 3D solid and the 2D shadow start at the same height — except where the 3D scene holds no solid for the parent at all (a parent wider than the scene's size limit of 10 km, or one whose outline cannot be built into a solid): there the 3D plant stands on the ground while its 2D shadow still starts from the parent's soil (ADR-037 addendum "base stacking", decision 5). **A garden bed with a height** exists only through its stored metadata (a generated or hand-edited plan, or an item that had a height before its type changed): the Properties panel offers no Height field for a garden bed that has none. **Known limits** (a plant can be IN raised soil without standing ON it, because links are not reconciled when a bed is created or resized — tracked as a follow-up): a raised bed drawn around an existing plant does not link it, so the plant stays at ground level (in 3D it is drawn inside the box); a climber linked to a trellis that stands in a raised bed stays at ground level, because a trellis holds no soil; a pot drawn on a raised bed stands on the ground, since only plants have a parent. **Stated exclusions**: parents do not stack; the Qt 3D viewer of US-E6, which extruded such a plant from the ground, was replaced by the workspace in Phase 17 L1.9 and deleted in L1.10. **3D shadows are not this requirement**: the sun study is the 2D model's. The Living Garden 3D meshes of fences, walls, buildings and pots are not the prisms the 2D model casts, and their shadows differ from it by measured amounts — a wall's is up to 24 % larger at a high sun, a picket fence's is about two thirds, a chain-link fence's under a fifth of the solid strip the 2D model casts; and a gabled building's 3D shadow ends short of the 2D one when the sun stands square to its ridge — by half the building's depth at a low sun (2.7 m for a 5.4 m deep house), because the 2D model casts a flat-topped block as high as the ridge (ADR-059, builders addendum; `scripts/measure_built_world_shadows.py`).

## FR-31: Per-object stacking order (issue #338, ADR-043)

- **FR-STACK-01**: A selected object (or multi-selection) can be **Brought to Front**, **Brought Forward**, **Sent Backward**, or **Sent to Back** — reordering it **within its own layer only**, never across layers. Reachable from: the Edit ▸ Arrange menu (`Ctrl+Shift+]` / `Ctrl+]` / `Ctrl+[` / `Ctrl+Shift+[`, mirrored by `Ctrl+Shift+Up` / `Ctrl+Up` / `Ctrl+Down` / `Ctrl+Shift+Down` on every action); each item's right-click context menu (`Arrange ▸` submenu, on every shape sharing the `GardenItemMixin` context-menu seam — rectangle, polygon, polyline, circle, ellipse, text, callout, group, smart symbol — plus arcs/beziers via the menu/shortcut without a context-menu entry); and the Properties panel's "Arrange" row (four icon buttons), shown for a single selected item and for a multi-selection.
- **FR-STACK-02**: A multi-selection keeps its members' **relative order** when arranged as a block; a selection spanning multiple layers is arranged one layer at a time (each layer's block moves within that layer only) but the whole gesture is **one undo step**.
- **FR-STACK-03**: A bed/container carries its **contained plants along as one block** — their relative order among themselves is preserved. A plant cannot be arranged **below its own bed**: `Send to Back`/`Send Backward` on a lone plant stops just above its bed, and if it is already there the action reports "already at back" rather than silently doing nothing. The same clamp applies to a `ROOF_RIDGE` and its owner polygon.
- **FR-STACK-04**: `Bring Forward`/`Send Backward` step the selection past the single **nearest item in the same layer whose scene bounding rect overlaps any member of the block** — a non-overlapping neighbour is skipped entirely. When there is no such item (or the block is already at the front/back of its layer), the action is a no-op and the status bar reports which: "Already at front", "Already at back", "No overlapping object in front", "No overlapping object behind", or "Select an object to arrange" for an empty/ineligible selection. A no-op pushes **nothing** onto the undo stack.
- **FR-STACK-05**: Every successful arrange is exactly **one undo step** (`ArrangeItemsCommand`), regardless of how many layers or how many items were affected.
- **FR-STACK-06**: Stacking order is persisted: `.ogp` objects are written **bottom→top** (fixing a pre-existing bug where every save/load round-trip inverted same-layer stacking) and each object carries an additive `stack_order` key when ranked. `FILE_VERSION` is unchanged — a file without the key loads in file order and is given honest ranks on that first load; a file with the key round-trips exactly. Copy/duplicate/paste preserve relative stacking order and the source layer (previously a pasted item was layer-less).
- **FR-STACK-07**: Journal pins are **not arrangeable** — no context-menu entry, no menu/shortcut effect, and the Properties panel shows no Arrange row for a pin-only selection. The Agent API's `arrange_object` refuses a pin the same way it refuses a locked-layer or group-member item.
- **FR-STACK-08**: The Agent API exposes a token-gated write tool `arrange_object(item_id, action)` with `action` one of `bring_to_front`/`bring_forward`/`send_backward`/`send_to_back`, applying exactly one undoable command through the same seam the GUI uses (bed block and plant clamp included) and raising on a no-op instead of reporting a false success. `ObjectRef`/`ObjectDetail` carry a read-only `stack_index` (0-based position within the object's layer, bottom→top, as displayed — compare only within one layer); `list_objects`/`objects_in_region`/`get_object` are documented as bottom→top in stacking order (`get_diagnostics` is not).

Acceptance: `tests/unit/test_stacking.py` (the Qt-free arrange algorithm — normalization, block expansion, all four modes, every outcome), `tests/integration/test_stacking_roundtrip.py` (the save/load inversion regression, rank round-trip, old-file compatibility, paste/duplicate ordering), `tests/integration/test_arrange_z_order.py` (every mode, undo/redo, multi-selection, bed block, plant clamp, cross-layer, move-to-layer interaction), `tests/integration/test_arrange_context_menu.py`, `tests/integration/test_arrange_menu_actions.py`, `tests/integration/test_arrange_properties_panel.py`, `tests/integration/test_agent_api_writes.py`, `tests/integration/test_agent_api_default_on.py`, `tests/unit/test_agent_api_queries.py`.

The clamp rule lives **once** in the Qt-free `core/canvas_bounds.py` (`clamp_shift_within_canvas`, `clamp_delta_within_canvas`, `rect_intersects_canvas`) and is called by **both** the GUI drag/nudge clamp and the agent path, so the two cannot drift; a parity test asserts the GUI `_clamp_items_to_canvas` produces the same shift as the shared function. `create_object` clamps the whole creation group (a HOUSE and its ridge move together); `move_object`/`set_object_position` clamp the moved group (the item plus any plants it carries) and trim an offset that would strand it to the canvas edge; `BackgroundImageItem` stays exempt, matching the GUI. The gross-input guard (`require_reachable_position`) still refuses absurd coordinates (e.g. `1e9`) and leaves the scene **and** the undo stack untouched. A **pre-existing** off-plan object (e.g. from an older file) is made discoverable: `ObjectRef`/`ObjectDetail` gain `outside_canvas` (bounding-box based; true only when the box does not overlap the canvas at all), and `get_diagnostics` gains an **`outside_canvas`** kind. Every clamped write is still exactly one undo step; a move whose delta the clamp erases entirely is refused as a no-op rather than pushing a dead undo step. This is a deliberate reversal of the earlier documented “stage an object just off-plan” rationale. No `FILE_VERSION` change. See ADR-036 addendum and §8.19.

### FR-SUN-09: Cached sun-requirement diagnostics (US-F3, #314)

- Explicit Hours of Sun computes the ground heatmap and per-plant ground-level estimates at sampled footprint centres, excluding the receiving plant's own caster and — for a plant that stands in a soil parent with a height (a raised bed, a container, a mounded bed: linked to it and its centre inside it, FR-SUN-11's membership) — that parent: the bed is under the plant, not between it and the sun. (In v1.30.1 only the plant's own caster was excluded, and every plant in a raised bed read 0 hours and warned.) Every other caster shades the plant as if it stood on the ground, and each casts from where it stands (FR-SUN-11) in the map and in the estimates alike. A plant inside a bed's outline WITHOUT a link to it stands on the ground inside the bed's solid and reads 0 hours. No computation before opting in to Hours of Sun; no leaf-height or translucent-canopy model.
- The single calendar in the permanent Plan & Sun strip owns the reference day. Today preserves the selected time. While Hours of Sun is enabled, date and exposure-input changes automatically refresh the map after debounce; the last completed map retains its actual date label while updating. Time-only changes preserve exposure. All results and the chosen date remain runtime-only (ADR-062).
- Nominal full-sun/partial-sun/partial-shade/full-shade bands are >=6/4-6/2-4/<2 hours. Warn only beyond one hour of tolerance: <5; <3 or >7; <1 or >5; >3, respectively. Exact tolerance boundaries do not warn. UNKNOWN never warns. Compare unrounded values, display one decimal, severity warning.
- Canvas badges, the shared Diagnostics panel and cached unauthenticated `get_diagnostics` agree. `sun_mismatch` details carry `hours`, `required`, ISO `reference_date`, `direction`, `measurement_method=ground_cell_centre_excluding_self`, and `receiver_id`. Enclosing objects are addressable navigation targets for grouped receivers.
- Missing, cancelled, stale, hidden and out-of-grid evaluations never become zero measurements or passed checks. Known unavailable requirements emit `sun_evaluation` with Information severity, reason and `status=not_evaluated`. Clear mismatches/badges within 100 ms after relevant edits; keep ordinary edited heatmaps only as explicitly stale snapshots. Requirement-only changes may reclassify valid results.
- A single selected TREE shows Under this canopy: other footprint centres inside/on its recorded mature max_spread_cm/2. Membership ignores guild/layer/bed, excludes the tree and sorts by enum layer, displayed name and UUID. Missing traits are Unspecified; missing mature spread is unavailable. Rows show dated cached hours or an unavailable hint. Geometric inclusion does not establish the cause of shade.

What the ranking does not know is a shape: a thin diagonal line counts as large, and a small surface on top of 256 larger ones is among those left out. Beyond 16,384 style elements or 32,768 dashes in a tile the rest is left out or drawn solid.
- **FR-3D-GROUND-05** (L1.5): The ground shows no seam between its tiles (measured luma spread across every tile border ≤ 0.7 of 255), a re-baked tile shows its new picture whichever tiles were re-baked before or after it, and the ground's memory does not grow with re-bakes: per tile one texture is held, plus the one it replaced until the next frame is shown. Measured for twenty full re-bakes of a 16 MB ground in the two cells the development machine offers: a software-rasteriser window that presents its frames (WARP, 40 frames presented in the twenty cycles: −0.02 to +0.03 MB a cycle, where keeping every replaced texture reads +32 MB) and a hardware-adapter window that presented NO frame (RTX 4070, 0 frames presented: −0.10 to +0.01 MB a cycle) — in which nothing is rendered, so that cell shows only that re-baking does not grow the process side. A hardware window that presents its frames is not automated; it is an item of the story's manual checklist (watch the process's commit size while dragging a lawn with the display on). *Known limit:* repeatedly taking a still frame from a live 3D view (`grab()`) whose window presents nothing grows a Direct3D 11 process by what each frame uploaded, until the view is closed; a screenshot is therefore taken through the offscreen path.
- **FR-3D-GROUND-06** (L1.5): Baking the ground never holds the application for a whole plan: one pass paints for at most 10 ms plus the one ground tile it is in — and one tile more when an edit arrives while older tiles are still waiting, so that a drag cannot starve them — and the tiles it has not reached keep their older picture (bare ground when a plan is first opened) until a later pass paints them, nearest to the last edit first. A ground tile that cannot be painted at all (no memory for its image) keeps its older picture, takes no other tile with it and is tried again with the next edit. Once no work is pending the ground is exactly the ground of one complete bake. A plan built to be slow can still make ONE tile cost seconds (measured: 0.9 s for a tile crossed by two styled paths of 16,384 points; 19 s for a tile under one comb-shaped polygon of 16,384 vertices — which the plan view itself needs 186 s to paint).

- **FR-3D-GROUND-07** (L1.5): The 3D view paints the plan's ground while the user works: an edit appears on the ground in the pass that applies it, and the tiles a time budget left are painted in passes of their own — each takes no reading of the whole plan — while the view is visible; a hidden view does no ground work and goes on when it is shown again. A new or opened plan never shows the previous plan's ground: a piece of the new ground not yet painted is bare meadow.
- **FR-3D-GROUND-08** (L1.5): What the 3D ground cannot show is reported, not hidden: an object whose paint on the ground failed is named in the list ("it could not be painted completely on the 3D ground") — it is shown, cut off, so the strip does not count it among the objects not shown in 3D — and the list opens with a note when the ground could not be finished (it is tried again with the next change), when places of the ground hold more surfaces than it can show (the smallest are left out), when pieces of it could not be painted (they show an older picture), or when the ground could not be painted at all; in each of these cases the strip says that the 3D ground does not show all of the plan. A ground that keeps failing never keeps the application busy: it is tried again with the next change of the plan. In the user's language (English, German, Spanish).

## FR-34: Plan timeline and plant lifetimes (US-F4, #315)

- **FR-TIMELINE-01:** One shared local plan date controls month scrubbing, Today,
  exact calendar dates, plant presence, sprite/3D growth and solar analyses.
- **FR-TIMELINE-02:** Optional removal dates round-trip additively; valid planting
  and removal edits each have one undo step and reject inverted/empty lifetimes.
- **FR-TIMELINE-03:** Plants before planting or on/after removal are hidden and
  unselectable; visible-set diagnostics exclude them. A named-date popover permits
  discovery and navigation. A non-today indicator identifies the viewed date.
- **FR-TIMELINE-04:** Visual exports reflect current visibility; PDF reports identify
  a non-today date. API objects retain absent plants and expose presence/as_of_date.
- **FR-TIMELINE-05:** Viewing dates never deletes plant data or changes yearly Season
  Manager copies. Generated plant tasks stop after removal, with surviving instances
  retaining a species schedule; manual tasks and succession dates remain independent.
