# ADR-032: Smart Symbol Format & Versioning (US-C4)

**Status**: **Superseded / removed (#1009).** The engine, persistence, properties-panel editing and DXF export were retired together; a plan that contains a symbol opens as a plain group with unchanged geometry (see the #1009 addendum). Historical decisions below; the UI was retired in #770.

**Status (historical)**: Accepted (Phase 13 - Package C, US-C4). **UI retired (#770):** the engine, persistence, properties-panel editing, and DXF export ship and are tested; the **Smart Symbols sidebar panel and the bundled starter set were removed in #770** (the fixed symbols added little over the parametric structure tools, #768/#769). Existing symbols in a loaded `.ogp` regenerate and export normally, and user files in `<app-data>/smart_symbols/` still load. The five former templates are test fixtures (`tests/fixtures/smart_symbols/`).
**Context**: Users want reusable **parametric blocks** ("raised bed L×W with N rows", pergola, fence panel) they can drop and edit by parameter rather than redrawing. The acceptance criteria require: a versioned, **user-extendable** definition format (drop a JSON → new symbol on next launch); the instance stores `symbol_id + version + params`, NOT the expanded geometry (it regenerates on load); a cached-geometry fallback for unknown/changed symbols; DXF export as BLOCK/INSERT; and a CI schema validator. A dropped JSON is untrusted input, so geometry expressions must be evaluated **without** `eval()`.
**Decision**:
- **Declarative geometry DSL.** A symbol JSON declares typed `parameters` (number/length/choice) and an `elements` list (`rect`/`line`/`polyline`/`polygon`/`circle`); each coordinate is a number or an arithmetic **expression string** over the parameters, and a `repeat{var,from,to}` block emits an element across an integer range. Bundled *and* user symbols are pure data — authoring a new shape needs no code. (`models/smart_symbol.py`, Qt-free, emits plain `PrimitiveSpec` dataclasses so generation is unit-testable.)
- **Safe evaluator, no `eval()`.** `core/parametric_eval.safe_eval` parses with `ast` and walks a strict whitelist (arithmetic + a fixed `min/max/abs/round/floor/ceil/sqrt`); attribute access, arbitrary calls, comprehensions, imports, and unknown names raise `ValueError`. No new dependency (no `jsonschema`/`yaml` — manual validation, like `amendment_loader`).
- **`SmartSymbolItem(GroupItem)`.** The canvas item is a `GroupItem` subclass whose children are the generated primitives, so it inherits selection/move/rotate, serialization-of-children, the type-dispatch sites that already treat groups correctly, and DXF export — only `regenerate_geometry()` is new (it rebuilds children from `definition.generate(params)`, preserving the group's position/rotation/layer). Children use **generic** shape types so a symbol stays decoupled from the bed/soil/plant systems that key off `object_type`; the definition's `object_type` field is reserved for a future styling pass.
- **Serialize as a group + metadata — no `FILE_VERSION` bump.** A smart symbol is written as `type:"group"` with an extra `smart_symbol:{id,version,params}` key and its generated children as the cached snapshot. An **older** app ignores the unknown key and loads it as a plain group (geometry preserved, parametricity lost); a **current** app reads the key and, if the live definition's `version` matches, regenerates — otherwise rebuilds from the serialized children and logs a warning. Stays at `FILE_VERSION` 1.4, consistent with the additive ethos.
- **DXF BLOCK + INSERT.** `dxf_service` emits one BLOCK per `(symbol_id, params)` (children in symbol-local coords) + an INSERT at the symbol's position/rotation, and skips the symbol's children in the flat-export loop so geometry is never double-exported.
- **Library (`services/smart_symbol_library.py`).** Bundled `resources/data/smart_symbols/*.json` load eagerly (a malformed bundled file is a packaging bug → crash loud); user `<app-data>/smart_symbols/*.json` load skip-with-warning (a bad user file must not break the app). A user file may override a bundled `id`. *(The app ships no bundled directory since #770; the loader keeps the mechanism for tests and user files — see the #768–#770 addendum.)*
**Alternatives considered**:
- *Built-in Python generators + JSON parameter manifest* — simpler/safer but **not** user-extendable for new geometry (a dropped JSON couldn't introduce a new shape without code), failing the core AC. Rejected.
- *A dedicated `SmartSymbolItem(QGraphicsItem)` with its own serializer/resize/snap plumbing* — the "~16 dispatch sites" surface rejected throughout Package C. The `GroupItem` subclass reuses all of it.
- *Bumping `FILE_VERSION` for a new `smart_symbol` type* — would make new plans unreadable by older apps. The group+metadata encoding degrades gracefully instead.
- *YAML / `jsonschema`* — extra dependencies for no real gain; JSON + manual validation + a dry-run `generate()` (the CI test) suffices.
**Consequences**: Smart symbols are a data-only feature — adding/curating symbols is editing JSON. i18n for symbol/param names is baked into the data (`name`/`name_de`, `label`/`label_de`, like `Amendment.display_name`), not Qt `tr()`; only the panel chrome went through `tr()`. A param edit is an undoable `ChangePropertyCommand` (apply_func = set param + regenerate). Rotated-symbol DXF INSERT rotation sign is a known nuance left for a follow-up (unrotated is exact). The former bundled starter set (`raised_bed_rows`, `greenhouse_gabled`, `pergola`, `fence_panel`, `compost_bay_3`) is the format's worked-example corpus in `tests/fixtures/smart_symbols/` since #770. Tests: `tests/unit/test_parametric_eval.py` (adversarial), `test_smart_symbol_model.py`, `test_smart_symbol_schema.py` (CI validator over every fixture file), `tests/integration/test_smart_symbols.py` (place/edit/undo/round-trip/missing-def/version-mismatch/DXF). This completes Package C (#188). **Known limitations (follow-ups):** rotated-symbol DXF INSERT rotation sign (unrotated is exact); a DXF block is keyed on `(symbol_id, params)` so two identical-param instances on different colours share the first instance's colour; `choice` parameter option strings have no `_de` localisation path yet (no fixture uses `choice`); editing a symbol definition's geometry without bumping `version` silently re-renders already-saved files (the version field is a strict geometry contract). Untrusted-JSON runtime errors (divide-by-zero, overflow, over-budget `repeat`) are caught at the `generate()`/`_resolve_specs` chokepoint and degrade to the cached geometry + a warning rather than crashing.

## Addendum (Issue #599 — Typed Smart-Symbol Members and Definition Versioning, 2026-11-02)

**Status**: Shipped in v1.34.13 | **Context**: issue #599, Slice B of 3D performance and correctness.
Smart symbol children previously instantiated exclusively as untyped/generic canvas items (`RectangleItem` with `GENERIC_RECTANGLE`, plain polylines, etc.). As a result, smart symbols containing garden beds (`raised_bed_rows`), greenhouses, compost bays, or fences were invisible to bed parenting, plant capacity accounting, soil diagnostics, 2D shadow casting, and 3D builders. Furthermore, regenerating geometry on parameter edits discarded and recreated children with random UUIDs, breaking any existing plant-to-bed parenting links.

**Decision**:
1. **Typed member resolution through canonical `_spec_to_item`**: Symbol element definitions declare `object_type` (matching `ObjectType` enum names, e.g. `"RAISED_BED"`, `"GREENHOUSE"`, `"COMPOST"`, `"FENCE"`). `_spec_to_item` instantiates the corresponding canonical item subclass (`BedItem`, `PolylineItem`, `RectangleItem`, etc.). Structural dividers use existing fence/wall primitives with explicit height.
2. **Construction guides**: Elements declared with `role: "guide"` (or `is_guide: true`) serve as 2D layout references and are explicitly excluded from 3D record snapshotting and shadow casting.
3. **Deterministic UUID derivation**: Generated children receive stable deterministic UUIDs computed from the parent symbol's UUID and element index / repeat key (`uuid5(symbol_uuid, key)`). On parameter edits, surviving children preserve their identities so child plants maintain their `parent_bed_id` links.
4. **Atomic undo and bed membership reconciliation**: Parameter changes run through `ChangeSmartSymbolParamCommand`, which regenerates geometry and invokes `_membership_change_for_geometry` in a single atomic undo/redo command.
5. **Definition versioning & read-only fallback**: Bundled symbols bump to `"version": 2`. When a plan is opened with an instance whose `symbol_version` is older than the library definition's version, the symbol retains its serialized children without silent regeneration. In the Properties panel, parameter editing is disabled with a translated explanation (`Symbol definition version mismatch — saved geometry is read-only.`).
6. **Zero `FILE_VERSION` bump**: Format remains additive via existing group metadata and child serialization. The Smart Symbols sidebar panel remains hidden per owner policy.

## Addendum (Issues #768–#770 — Parametric Structures Replace the Fixed Templates, 2026-11-08)

**Status**: Shipped in v1.37.9 (PR #779). **Context**: the Smart Symbols panel was already hidden, and its fixed templates (a gabled glasshouse, a pergola) were the wrong abstraction for the owner's workflow: both objects need to scale with the plan and match their 3D build. Two first-class parametric tools replace them.

**Decision**:
1. **Pergola is a parametric structure, not a symbol.** `core/pergola.py` is the ONE layout (posts, perimeter beams, rafters, purlins); the canvas painter (`ui/canvas/items/pergola_paint.py`), the gallery thumbnail and the 3D builder (`core/scene3d/builders/structures.py`) all read it. The old `pergola.svg`, its generator recipe and the bundled `pergola` symbol are retired.
2. **Greenhouse is a ridge-bearing building.** `RIDGE_BEARING_KINDS = {HOUSE, GREENHOUSE}` and `is_ridge_bearing_kind`/`is_ridge_bearing_type` are the one predicate every ridge path uses (polygon tool, type change, copy, move/resize, snapshot, agent create, load sanitisation). Its ridge is anodised aluminium (`#B0B5B9` / `#9EA3A8`, `ridge_finish: "aluminium"` metadata) rather than the house's brown; the 2D glazing bars and the 3D frame share `core/greenhouse.py`'s bay count. The bundled `greenhouse_gabled` symbol is retired.
3. **The panel and the bundled definitions are removed.** `ui/panels/smart_symbols_panel.py`, its `SidebarController` registration, `application._on_smart_symbol_selected` and `resources/data/smart_symbols/` are gone. The five JSON definitions moved to `tests/fixtures/smart_symbols/` so the DSL, typed members, bed links, undo and serialization stay covered. `SmartSymbolItem`, `services/smart_symbol_library.py` and the cached-child fallback remain for existing plans and user files.
4. **Sprite orientation is one shared rule (#776).** `core/sprite_orientation.py` owns the natural footprint table and `sprite_turn_deg`; the 2D renderer renders at the swapped size and turns the pixmap, and `kit.object_box`/`placed` build the same turned mesh. The renderer's default dimensions are derived from that table, so they cannot disagree.
5. **No `FILE_VERSION` bump.** Existing plans keep their stored smart-symbol children and ridge colours; only new ridges get the aluminium finish, and the `ridge_finish` key is additive (a ridge without it paints brown).

**Consequences**: The fixed-symbol library is no longer a product surface; the parametric tools are. The version contract (FR-SYMBOL-08) still guards user files and existing plans. Tests: `tests/integration/test_parametric_structures.py` (layout, 2D/3D agreement, greenhouse ridge lifecycle), `tests/unit/test_sprite_orientation.py`, the extended `tests/integration/test_smart_symbols.py` (fixture library), and the ridge cases in `tests/integration/test_house_roof_ridge.py`.

## Addendum (issue #1009, 2026-11-25 — Smart Symbols are removed completely)

**Status**: Shipped in v1.43.3 (PR #1030, 2026-11-27); owner manual tests passed on 2026-11-27. **Context**: #770 removed only the panel and the bundled set. Since v1.37.9 no user could create a symbol, yet the engine, persistence, Properties-panel editing, DXF block export, the `<app-data>/smart_symbols/` folder contract and their tests were still on `master`.

**Decision**:
1. **The engine is gone, not hidden.** `models/smart_symbol.py`, `services/smart_symbol_library.py`, `ui/canvas/items/smart_symbol_item.py`, `ChangeSmartSymbolParamCommand`, the DXF BLOCK/INSERT export path, the Properties-panel parameter editor and the Smart-Symbol metadata consumers in the shadow and 3D snapshot paths are deleted. `models/parametric_eval.py` stays as a generic bounded arithmetic evaluator (its own unit test is the only remaining caller).
2. **Old plans open as plain groups.** The loader ignores a `smart_symbol` key instead of reconstructing a symbol; the serialized children remain the geometry. Typed children (#599) keep their types. The next save writes a group without the key. No `FILE_VERSION` bump, exactly as this ADR designed.
3. **User data is untouched.** `<app-data>/smart_symbols/` is no longer read and is deliberately not migrated or deleted (the same rule as #767).
4. **The group rotation key is additive.** A group now stores its own `rotation` (issue #1022), which also preserves the angle a pre-removal symbol could carry. Older apps ignore it.

**Consequences**: the removal is pinned by `tests/integration/test_smart_symbol_removal.py` (an old plan with the key opens as a two-member group with the same types and positions, and a re-save drops the key). The translation gate loses the `SmartSymbolsPanel` context and the "Smart Symbols" menu string in all five locales. The broader trust-boundary lesson from PR #236 stays in the pitfalls file, but its pinned test and model reference are gone.
