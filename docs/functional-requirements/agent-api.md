# Agent API

## Embedded MCP server

- **FR-AGENT-01**: The app can host an **MCP server over streamable-HTTP** for AI agents (Claude, Cursor, any MCP client), embedded in the running GUI on a background thread and reachable at `http://127.0.0.1:<port>/mcp`.
- **FR-AGENT-02**: The server is **on by default** (read-only) so AI assistants can connect without users hunting through Preferences. A Preferences → **Agent API** group (Enable checkbox + Port spin-box 1024–65535 + read-only connect-URL label) persists in `AppSettings` (`agent_api/enabled` default **on**, `agent_api/port` default **8765**); it **auto-starts on every launch** and users can disable it there.
- **FR-AGENT-03**: The server binds **127.0.0.1 only** (never the LAN). Read tools use the D1 loopback-trust model; every scene-mutating D2 tool, including global `undo`/`redo`, is additionally gated by the writes-enabled setting and the bearer token defined in FR-AGENT-13/ADR-036. A port already in use is reported in the status bar without crashing.
- **FR-AGENT-04**: Tool **`get_plan_summary`** returns a curated, stable summary of the open plan: bed/plant/other-shape counts, canvas size (cm), layer names, file name, and unsaved-changes flag. Reading the plan never mutates it.
- **FR-AGENT-05**: Agent reads and D2+ edits are marshaled onto the Qt main thread; the server stops cleanly when the toggle is turned off and on app close. Tool/resource/prompt descriptions are an English API contract (exempt from i18n); only the Settings UI strings are translated.
- **FR-AGENT-06**: **`list_objects(type?, layer?, parent?, raw?)`** enumerates top-level objects; **`get_object(item_id, raw?)`** returns one object's full detail. Objects are addressed by stable UUID; `type` accepts an `ObjectType` name, a category (`bed`/`plant`/`shape`), or a geometry kind. Both return the curated schema (`ObjectRef`/`ObjectDetail`), or the raw serialiser dict(s) when `raw=true`.
- **FR-AGENT-07**: Spatial tools locate and measure objects in scene centimetres: **`objects_in_region(x, y, width, height)`** (bounding-box intersection), **`objects_in(parent_id)`** / **`plants_in_bed(bed_id)`** (container contents), **`nearest_objects(x, y, k?, type?)`**, and **`measure_distance(id_a, id_b)`** (centre-to-centre). Coordinates are the native scene frame (CAD Y-up per ADR-002: origin bottom-left, +x east/right, +y north/up — a larger y is further north); non-rectangular shapes use their bounding box.
- **FR-AGENT-08**: **`get_diagnostics(kind?)`** reports the plan's current warnings — companion conflicts, spacing overlaps, soil/pH mismatches, container capacity overruns, and crop-rotation conflicts — by reading the **already-computed** flags the canvas shows as badges (no recomputation). Positive indicators are not reported.
- **FR-AGENT-09**: **`render_canvas_image(x?, y?, width?, height?, layers?, image_width_px?)`** returns a PNG screenshot of the live canvas (a region in scene cm, or the full canvas by default) plus a structured `RenderMeta` block (rendered region, output pixel size, `px_per_cm`, layers actually shown). `layers` is an optional layer-name allowlist (unknown names match nothing, not an error) that **overrides** what's currently shown — a layer the user has toggled off in the live Layers panel is rendered anyway if requested, and every layer's visibility is restored to its prior state afterward. Output width is clamped to 128–2048px (default 1024), with the derived height independently clamped to the same bounds. Selection handles and construction geometry are never shown. The image's pixel Y-axis is inverted relative to the native scene frame (FR-AGENT-07) — `RenderMeta.px_per_cm`'s description documents the exact correction formula. Reading/rendering the plan never mutates it or the user's live selection.
- **FR-AGENT-10**: **`save_plan(file_path?)`**, **`export_pdf(file_path?, paper_size?, orientation?)`**, **`export_dxf(file_path?)`**, and **`export_csv(kind, file_path?)`** write a file to disk via the same services the GUI's File > Export/Save menu uses — the PDF report, a DXF drawing, or a CSV (`kind` = `'shopping_list'` or `'harvest'`), and the project's own `.ogp`. None of these mutate the in-memory plan except `save_plan`, which persists what's already on screen (mirroring the GUI's save path exactly, including its stale-shopping-list-price cleanup) — no token auth is required (reserved for D2's scene-mutating write tools). Omitting `file_path` writes to a sensible default next to the currently open project (or the app's Documents folder); `save_plan` with no project open and no `file_path` raises rather than inventing a filename, mirroring the GUI's own Save-As requirement for a brand-new project. Given an explicit `file_path`, the destination's parent directory must already exist, and — unlike a `QFileDialog` save prompt — an unrelated existing file at that path is overwritten without confirmation. All four return a shared `ExportResult` (written path, format, row count for CSV, and — for `save_plan` — the project's prior file path if the call redirected it).
- **FR-AGENT-11**: Five read-only MCP **resources**: **`garden://plan`** (curated `PlanSummary` — same data as `get_plan_summary`), **`garden://plan/raw`** (the uncurated snapshot dict), **`garden://canvas.png`** (a PNG of the full live canvas, no region/layer args — same pipeline as `render_canvas_image`), **`garden://diagnostics`** (same data as `get_diagnostics`), and **`garden://species`** (the bundled species database — 118 records, static data with no `AgentProviders` field or main-thread hop, since `services/bundled_species_db.py` has no Qt dependency). Two read-analysis **prompts**: **`audit-plan`** (plan summary + current diagnostics, asks for prioritized improvement suggestions) and **`describe-garden`** (plan summary + object list, asks for a narrative description) — both compose live data via a new Qt-free `agent_api/prompts.py`, no write/guided-edit prompts (deferred to D3). Verified directly against the installed `mcp==1.28.1` source: resource functions returning `bytes` with an explicit `mime_type` produce a base64-encoded `BlobResourceContents` automatically (no `Image`/`structured_output=False` workaround, which is tool-only), and non-`str`/`bytes` returns (a pydantic model, a `dict`, a `list`) auto-serialize to JSON text via `pydantic_core.to_json`.
- **FR-AGENT-12**: A discoverable **"Connect AI Assistant…"** entry point (Help menu, and a matching button in Preferences → Agent API) opens a dialog showing the connect URL (Copy button) and the transport (Streamable HTTP). The dialog **detects** installed AI clients by their known config locations — **Cursor** (`~/.cursor`), **Claude Code** (`claude` CLI on `PATH` or `~/.claude.json`), **Claude Desktop** (the platform app-data folder) — and offers **one-click registration** where each client's own documented mechanism supports a safe automatic path: a direct JSON merge into `~/.cursor/mcp.json` for Cursor, and for Claude Code the `claude mcp add --transport http --scope user` CLI when it's on `PATH` — **and, when it isn't, a direct atomic merge into `~/.claude.json`'s top-level `mcpServers`** (the same user-scope `type: "http"` entry the CLI writes, read by both the CLI and the VS Code extension), so a machine without the CLI still gets a working one-click. **Claude Desktop is detection-only and cannot reach a localhost server at all** — its connectors are reached from Anthropic's cloud and reject `localhost`/`http://` URLs — so its row shows an honest "use Claude Code or Cursor instead" note, with no button and no snippet. Every client with an automatic path also gets a copy-paste JSON snippet with a short "where to put this" note. Automatic writes preserve every other key/server in the target file, back up its current contents before touching it (a second run's backup reflects the most recent pre-write state, not the pristine original), and write atomically (temp file + rename) — never clobbering existing configuration. The connect URL always comes from asking whether the server is actually running, never reconstructed from settings — a saved port can still be dead (e.g. a port conflict at launch). The merge into `~/.claude.json` (which also holds OAuth tokens and project trust) fails **closed** — an unreadable file is left byte-for-byte untouched rather than replaced. The dialog's client rows sit in a scroll area, so revealing a manual snippet scrolls it into view instead of clipping it behind the Close button. No token auth is needed (registering a client isn't a scene-mutating action). See ADR-035 (and its issue-#253 addendum).
- **FR-AGENT-12a** (issue #366, **generalized client onboarding**): the onboarding surface is **registry-driven** — each client is one frozen `ClientTarget` record, and the three things that genuinely differ between clients are independent fields (`container_key`: `mcpServers` / `mcp_servers` / the NESTED `mcp.servers`; `syntax`: `json` / `jsonc` / `toml`; `entry` / `cli_argv`) rather than branches, so the dialog gained a row for a new client with no vendor-specific code beyond one completeness-tested note. Backup-before-write, atomic replace, fail-closed on a `foreign` file, and foreign-key preservation exist **once** in a shared merge keyed on `syntax`. Three clients are added (**OpenCode**, **Codex**, **Gemini CLI**); Claude Desktop stays detection-only. The **JSONC** reader tolerates comments and trailing commas by character scan (so a `//` inside a string survives) while the strict `json` reader still raises, so leniency cannot leak into the fail-closed path. **TOML is appended surgically** — `tomllib` reads and validates, and only the one table's line span is rewritten — because a full re-serialise would discard the user's own comments in a file OGP does not own; **no new dependency**. A **CLI wins over a direct merge** when the client ships one, and the merge is a supported route rather than a degraded one. **The read-only connect URL is the default hand-out**: the primary copy action carries no `?token=`, and the write URL sits behind a separate action that states the credential is in it — the generic fallback text is read-only for the same reason. Each client additionally reports **detected / registered / stale** from a per-target read, so a rotated token or a changed port surfaces as "add again to update" instead of a registration that looks fine and silently cannot connect. See ADR-035's issue-#366 addendum and FR-AGENT-12.
- **FR-AGENT-13** (US-D2.0, the first agent **write** tools): with **"Allow AI assistants to edit the plan"** enabled in Preferences → Agent API (**off by default**), the server exposes two scene-mutating tools — **`move_object(item_id, dx, dy)`** (move by a relative offset in scene cm; the canvas is Y-up per ADR-002, so a positive dy moves the object north and a negative dy south — the same frame the read tools report; a bed/container/trellis carries its contained plants along, and a moved plant has its bed membership re-evaluated afterward, mirroring the GUI's own drag-release behaviour) and **`delete_object(item_id)`** (detaches contained plants, removes any constraint referencing the object, and deletes a `HOUSE`'s linked roof ridge — all matching the GUI's own delete orchestration, not just its `DeleteItemsCommand`) — each requiring a bearer token and each applied via the same `command_manager.execute` path the GUI uses (Ctrl+Z reverses it, and it marks the plan dirty). `delete_object` is one undo step; `move_object` is one step — including when the move reparents a plant across a bed boundary, since #443 reconciles membership inside the move command itself — never more. Both tools **refuse** (raise a clear error) rather than silently mishandle cases outside their supported contract: an object participating in a geometric constraint (per the final D2.6 contract, agent geometry writes permanently refuse rather than silently skipping `CanvasView`'s multi-item live solver; `get_geometry` exposes the blocking constraint), a journal pin (its delete needs a `ProjectData` note-record prune a bare `DeleteItemsCommand` doesn't do), an object on a **locked layer** (the GUI makes locked-layer items entirely non-interactive; the agent must honour that protection too), and an individual **group member** (the GUI only ever moves/deletes the whole group — address the group by its own id). **Write tools are gated two ways**: they are registered only when editing is enabled **and** a token is configured (otherwise they don't appear in the tool list at all), and every call must present the token — **either in the server URL as a `?token=` query parameter (the reliable route: some clients, notably Claude Code on streamable-HTTP, store a configured header but don't send it on tool-call requests) or as an `Authorization: Bearer <token>` header** — an unauthenticated or wrong-token call fails and leaves the scene untouched. Reads remain open (loopback trust, unchanged), so this doesn't affect clients that only read. The token is **auto-generated** (shown with Copy/Regenerate in Preferences, and injected into each client's config by the "Connect AI Assistant" dialog as a `?token=` on the connect URL); regenerating it revokes prior clients. Delivering the secret in the URL means it can appear in local request logs — an accepted, loopback-only exposure (the same secret already lives in the client's config). No `FILE_VERSION` change. See ADR-036. Later D2 stories add create/resize/rotate/species/reparent/layer tools behind the same gate; D3 adds domain-intelligence + guided-edit prompts.
- **FR-AGENT-14** (US-D2.1, agent **object creation**): behind the same two gates as FR-AGENT-13 (editing enabled **and** a valid token), the server exposes **`create_object(object_type, x, y, width?, height?, radius?, name?, species?)`**, which adds one new object to the plan. Scope for this slice is **plants + soil containers**: the round types **TREE**, **SHRUB**, **PERENNIAL** (radius optional — omitting it uses the app's own gallery-drop defaults of 100/50/30 cm) and **CONTAINER_ROUND** (radius required — a pot has no house default), plus the rectangular **GARDEN_BED**, **RAISED_BED**, **CONTAINER** and **WALL_PLANTER** (both `width` and `height` required). `x`/`y` are the object's **centre**, in the same Y-up scene frame the read tools report (a larger y is further north), so an agent can place an object relative to one it just read without converting anything; the centre→anchor conversion for rectangles is `anchor = centre − extent/2`, which holds in either y-direction reading and so cannot introduce a Y-flip error. The item itself is built by **`ProjectManager._deserialize_item_core`** — the `.ogp` loader's own factory — so an agent-created object is constructed by exactly the code path a loaded one is, adding no second item-construction path to drift. The tool mirrors the GUI's gallery-drop orchestration rather than just `CreateItemCommand` (with one deliberate omission: the drop handler also sets `plant_category` from the gallery's drag payload, which `create_object` does not expose — the SVG resolver's species tier covers the useful case, and the category tier is simply unreachable for agent-created plants): a `species` matching the bundled database is **auto-populated** into the item's species metadata (so the plant-detail panel and FR-SOIL mismatch warnings light up without a manual search), **every** new plant is stamped with today's **planting date** — deliberately whether or not a species was given, since a placeholder that gains a species later must not be left permanently undated for the growth/shadow/heatmap/3D views (FR-SUN-08) — and the object lands on the **currently active layer** (or on no layer at all when the scene has none active — matching the GUI drop path). Two asymmetries are stated rather than hidden: a **locked** active layer is refused, but a **hidden** one is silently un-hidden by `QGraphicsScene.addItem` (as it is for the GUI's own draw tools) and **undo does not re-hide it**, so that one visibility change sits outside the undo step. A plant created inside a bed is linked to that bed **within the single create step** (`CreateItemCommand.execute` already calls `_auto_parent_plant`, and its `undo` calls `_detach_from_parent`), so this is **always exactly one undo step** (as is `move_object`, whose own reparent is reconciled inside the move command since #443); the resulting parent is reported as `new_parent_bed_id` while `bed_membership_changed` stays false, because no separate reparent operation happened. The tool **refuses** (raises a clear error naming every supported type) rather than guessing: an object type outside the slice, a dimension that doesn't fit the type's shape (`width` on a round type, `radius` on a rectangular one), a missing required dimension, a zero/negative extent, a non-finite (NaN/infinity) coordinate or extent, a **species on a non-plant type** (the only silent-ignore an otherwise loud tool would have had), an **implausibly large extent** (capped at twice the plan's larger canvas dimension, and additionally at 5000 cm for a plant, whose footprint drives a quadratic main-thread `QImage` allocation sized in scene centimetres — the shape of a metres-for-centimetres unit slip), a **position further than one canvas beyond an edge** (unreachable by any GUI gesture), and a **locked active layer** — the GUI cannot draw onto a locked layer either. Every refusal leaves the scene and the undo stack untouched. Parameter validation lives in the Qt-free `agent_api/creates.py`, whose object-type name sets carry drift guards against the real `ObjectType` definitions. No `FILE_VERSION` change. See ADR-036 (US-D2.1 addendum).
- **FR-AGENT-15** (US-D2.2, agent **resize + rotate**): behind the same two gates as FR-AGENT-13 (editing enabled **and** a valid token), the server exposes **`resize_object(item_id, width?, height?, radius?)`** and **`rotate_object(item_id, angle, relative?)`**, completing core single-object manipulation (create / move / delete / resize / rotate). Dimensions are **absolute targets in centimetres**, the same vocabulary `create_object` uses — `radius` for round objects, `width` and/or `height` for rectangular ones, either axis alone leaving the other unchanged. **The object's scene centre is preserved for every type**, so the coordinates an agent read before the resize remain valid afterwards; the resulting centre is echoed back from the same source the read tools use. `rotate_object` takes **degrees, positive = counter-clockwise** — an object whose long axis points east points north after `+90`; this convention was determined by measuring a real item rather than assumed, and is pinned in two test suites against a corner position before and after (never against the stored angle), because issue #267 is what a docstring stating a frame the code doesn't honour costs. Rotation is **absolute by default** (calling it twice with 90 leaves the object at 90) with `relative=True` to accumulate; the result is normalised into `[0, 360)` and reported as `rotation_deg`. A **group** is one addressable object: `rotate_object` turns it about the pivot fixed at its first turn rather than a recomputed centre, carries a grouped bed's linked top-level plants about that same pivot in the same undo step, and refuses when any member or carried linked plant is constrained or on a locked layer, when a linked plant is owned by another group, or when a grouped bed's linked plant would be separated. A requested orientation equal to the current one is a **no-op**: no pivot
is fixed, no link is reconciled and no undo step is added. Both tools apply exactly **one undoable step** — a bed resize or rotate re-decides only that bed's plants, inside the same step (#443) — and both route through **`ui/canvas/geometry_apply.py`**, the canonical geometry-apply path this story extracted so that every rect-backed caller shares one function instead of one closure apiece (`apply_rotation` now has exactly one definition in the codebase; the authoritative list of callers and the two deliberate exceptions is that module's own docstring, stated there only). That extraction also **fixed three live GUI bugs it exposed, none of them introduced by this story** — all exactly 0 at rotation 0, which is why none had ever been reported: the properties panel's numeric resize displaced a rotated object by **73.2 cm** (30° / 50→100 cm); the vertex-edit corner drag left the stored centre **331 cm** from the visible one; and the EQUAL-constraint partner resize moved a size-linked rotated partner by **70.7 cm** at 90°. The tools **refuse** (raise a clear error, leaving the scene and undo stack untouched) rather than guessing: a **vertex-backed** object (polygon/polyline — refused by name, with vertex editing deferred to a later slice), a dimension that doesn't fit the object's shape, no dimension at all, a zero/negative/non-finite extent, an extent below the 1 cm floor the GUI itself enforces or above D2.1's canvas-relative cap (plus the plant-diameter cap), a non-finite or implausibly large angle, an object participating in a **geometric constraint** (the live constraint solver has no one-shot equivalent, so editing would silently violate the constraint), and — through the write path's shared resolver — a journal pin, a group member, or an object on a **locked layer**. Validation lives in the Qt-free `agent_api/edits.py`. No `FILE_VERSION` change. See ADR-036 (US-D2.2 addendum).
- **FR-AGENT-16** (US-D2.3, agent **species assignment + explicit bed reparenting**): behind the same two gates, the server exposes **`set_species(item_id, species?, apply_database_size?)`** and **`set_parent_bed(item_id, bed_id?)`**, closing two gaps that only existed for objects that *already* exist. `set_species` gives a plant the user drew by hand a species — resolved against the **bundled database** by scientific name, common name or alias through the same resolver `create_object` uses — which is what makes the plant-detail panel, the planting calendar and the FR-SOIL mismatch warnings apply to it; `species=null` clears it. Assignment goes through **`ui/plant_species_assignment.apply_species_to_item`**, the helper issue #213 extracted so the plant-database panel and the species search cannot diverge, making the agent a third caller rather than a third implementation. As in the app, the drawn footprint adopts the species' real mature size (diameter = `max_spread_cm`); **`apply_database_size` (default `true`) is the agent's answer to the two-button dialog the GUI shows when a manual `spacing_radius_cm` override disagrees with the database** — `true` takes the database values and clears the override, `false` keeps the user's — and is **not** a general "don't resize" switch, since without a conflicting override the footprint adopts the database size either way. The deliberate asymmetry with `create_object` (which sizes a new plant from the gallery defaults, because `radius` is an explicit creation parameter that a species must not silently overrule; the GUI's own gallery drop sizes a *named* species from `max_spread_cm` (FR-PLANT-15), while `create_object` keeps its explicit `radius`) is documented rather than reconciled: an agent wanting a database-sized new plant calls `create_object` then `set_species`. `set_parent_bed` links a plant to a bed or detaches it (`bed_id=null`) as a **link change only — the plant does not move**, reaching the one state `move_object` cannot: a plant already sitting inside a bed drawn around it and therefore never linked. It **deliberately does not require geometric containment** (the app's own Link action does not either, and requiring it would defeat the tool's purpose); the result's `link_is_geometric` reports whether the link and the geometry agree. Since #443 it is the SAME standing point the sun study and the Living Garden 3D scene use — the plant's stable geometric centre, which no warning badge or highlight can move — so it cannot disagree with the lift's containment half; `true` still does not by itself mean the plant is lifted (a trellis, an in-ground bed or a hidden parent holds it on the ground). The field's description in the tool schema says so, in the words an agent reads. A plant's parent may be any soil container **or a `TRELLIS`** — which holds plants but has no soil, per §8.14/ADR-017 — and anything else is refused by name with the valid options listed. z is derived from the normalized stacking order (issue #338), so no z snapshot is taken or restored; soil-mismatch diagnostics are refreshed explicitly because parent-link mutations don't fire `QGraphicsScene.changed`. Because assigning a species resizes the footprint, `set_species` is a geometry mutation and **refuses a constrained object** exactly as `resize_object` does — otherwise an agent blocked by one tool could obtain the same resize through the other; clearing a species resizes nothing and is not gated. Both tools apply exactly **one undoable step**; both **refuse** (leaving scene and undo stack untouched) on a non-plant object, an unknown species name, a target that cannot hold plants, a **no-op** (linking a plant to the bed it is already in, or clearing a species that was never set), a journal pin, a group member, or a **locked layer**. `WriteResult` gains `species_key` and `link_is_geometric`. No `FILE_VERSION` change. See ADR-036 (US-D2.3 addendum).
- **FR-AGENT-17** (US-D2.4, issue #328, agent **layer tools**): behind the same two gates, the server exposes unauthenticated `list_layers()` and the write tools `set_object_layer(item_id, layer_id)`, `create_layer(name)`, `rename_layer(layer_id, name)`, `delete_layer(layer_id)`, `set_active_layer(layer_id)`, and `set_layer_property(layer_id, visible?, opacity?, locked?)`. Layer ids are stable UUID strings; names remain available for display and backwards compatibility but are not write addresses. The curated schema reports each layer's name, visibility, lock state, opacity, z-order, active flag, and top-level object count; objects additionally report `layer_id`, and render allowlists accept either layer ids or names. Every document mutation uses the existing layer command path and is exactly one undo step. `set_active_layer` changes session state only and deliberately has no undo entry. **Layer locking is agent-writable in both directions (policy reversed by issue #365):** `set_layer_property(layer_id, locked=...)` locks and unlocks through the same `SetLayerPropertyCommand` the Layers panel's own lock toggle runs, as exactly one undo step. What is unchanged is the *object-level* protection, which tests the layer's **current** lock state: agents still may not delete a locked layer, move objects onto it, or edit its objects — so an agent that needs to edit a locked layer unlocks it first and edits second, two ordinary undoable calls the user can see and reverse. Passing two properties in one call still refuses before any command is built, so a mixed call can never half-apply. Deleting an unlocked layer follows the existing command policy and moves its objects to the replacement layer in the same undo step, so undo restores both the layer and assignments. Refusals leave the scene and undo stack untouched. No `FILE_VERSION` change. See ADR-034/036 addenda and §8.19.
- **FR-AGENT-18** (US-D2.5, issue #329, agent **shape and structure creation**): `create_object` keeps the D2.1 double gate, active-layer assignment, GUI defaults, plant parenting, planting-date stamp, and one-undo contract, and adds canonical circle, rectangle, ellipse, polygon, polyline, and callout families from the `ObjectType` roster. Rect-like families take centre plus centimetre extents; polygons accept either explicit `points` or a rectangular centre/width/height convenience form; polylines take at least two points; callouts take a leader-tip `x`/`y` and text with optional **signed, finite** box offsets. Each callout offset, including a resolved default, is bounded at the API boundary to `abs(offset) <= 2 * max(canvas_width_cm, canvas_height_cm)`; valid negative and default offsets remain accepted on normal-sized plans, while explicit null/non-finite/oversized values are refused before Qt construction and leave the scene and undo stack untouched. All coordinates and vertices use the native scene CAD Y-up frame, with no Y flip. Objects are constructed by `ProjectManager._deserialize_item_core`; a `HOUSE` additionally creates its linked `ROOF_RIDGE` through the shared Qt geometry-only helper and one `CreateItemsCommand`. `list_creatable_types` returns the machine-readable family contract and deliberate refusals. The approved D2.5 contract recorded in the issue-237 implementation session deliberately refuses direct `ROOF_RIDGE`, `GARDEN_JOURNAL_PIN`, `GENERIC_TEXT` (no round-trip support), and legacy `HEDGE_SECTION` creation, with reasons. The creatable-plus-excluded union is drift-guarded against `ObjectType`; no `FILE_VERSION` change. See ADR-036, FR-AGENT-18, and §8.19.
- **FR-AGENT-19** (issue #353, **global history and load lifecycle**): authenticated MCP `undo()` and `redo()` operate on the same global GUI/agent LIFO `CommandManager` stack, reverse or reapply exactly one command per call, return the command description plus post-call `can_undo`/`can_redo`, and explicitly refuse an empty stack rather than reporting a no-op as success. Project loading removes every serialized document item (including callouts and Arc/Bezier items) before rebuilding, while preserving the dedicated compare/dimension overlay cleanup; `list_layers.object_count` therefore agrees with the top-level objects returned by `list_objects` after a same-scene save/load. Agent delete refuses duplicate live IDs and returns success only after the target (and linked roof ridge) is detached from the scene.
- **FR-AGENT-20** (issue #355, **bounded callout input**): `create_object` validates callout `box_dx`/`box_dy` at the MCP boundary before `_deserialize_item_core` or any `CreateItemCommand`; values must be finite and signed within the canvas-relative contract `abs(offset) <= 2 * max(canvas_width_cm, canvas_height_cm)`. The same check applies to the resolved default offsets, so a tiny plan cannot silently receive a geometry outside its declared bound. Explicit JSON null is rejected as well as Infinity/NaN and oversized finite values, so a JSON stack that normalizes non-finite numbers cannot turn hostile input into a default offset. Valid negative/default offsets, save/load, rendering, deletion, and the scene/undo stack remain unchanged on the normal path.
- **FR-AGENT-21** (US-D2.6, issue #330, **low-level geometry escape hatches**): the server exposes unauthenticated **`get_geometry(item_id)`** plus token-gated **`set_object_position(item_id, x, y)`**, **`set_vertex(item_id, index, x, y)`**, **`add_vertex(item_id, index, x, y)`**, and **`delete_vertex(item_id, index)`**. `get_geometry` is a curated live-Qt read, not the raw serializer: it reports the same centre semantics as `get_object`, local native extents/radius and rotation, current scene-frame polygon/polyline vertices, Arc/Bezier/construction-line/leader data where applicable, vertex capability/minimum count, and every referencing constraint in deterministic order. The read/write frames agree: converting a live scene vertex back to local coordinates reuses the exact current `QPointF` when the request is unchanged, so inverse-transform noise cannot masquerade as a mutation. An unchanged `set_vertex` request is refused as a no-op — no command, no history entry, no dirty state — consistent with the other no-op refusals. Moving a vertex and setting it back leaves the serialized object byte-identical. Absolute positioning produces the same result as the equivalent `move_object` delta and shares its logical-bed-child propagation and plant-reparenting behavior. Vertex writes support polygon and polyline items only, preserve minima of 3 and 2 vertices respectively, and each actual set/add/delete is exactly one undoable command; a HOUSE roof ridge remains attached through the existing polygon reprojection hook. All scene points must be finite and within the same canvas-relative reachability bound as `create_object`. Every geometry-changing tool permanently refuses a constrained object and names the blocking constraint; `get_geometry` remains readable so an agent can explain the refusal. Group members and journal pins remain non-addressable, locked-layer objects remain readable but unmodifiable, and duplicate live UUIDs fail closed. Arrays, booleans, trim/extend/fillet/chamfer, align, mirror, group/ungroup, and solver-backed constrained writes remain explicitly deferred. No `FILE_VERSION` change. See ADR-036 D2.6 addendum and §8.19.
- **FR-AGENT-22** (issue #365, **document lifecycle**): the server adds two token-gated tools, **`new_plan(width_cm?, height_cm?, force?)`** and **`open_plan(file_path, force?)`**, so an agent is not limited to whatever plan the user happens to have open. Both are gated exactly like `delete_object` — not merely because they mutate, but because they can **discard unsaved work** — and both are listed in the `WRITE_TOOL_NAMES` drift guard so a refactor that moves one outside the gate fails a test. Both reuse the GUI's own paths: `_on_new_project` was extracted into `_new_project_document`, and `_open_project_file` was split into a raising `_load_project_file` plus its modal-reporting GUI wrapper, so an agent never has a `QMessageBox` appear on its behalf. Each **refuses when the open plan has unsaved changes unless `force=true`** — the GUI asks the user at that point and an agent cannot, so the choice is binary — and a refusal leaves the document untouched. `new_plan` keeps the current canvas dimension for any argument omitted, and **refuses** a non-finite or out-of-range (50–100000 cm) dimension rather than clamping, because a clamped canvas is a silently different plan than the one requested. `open_plan` requires an existing `.ogp` **file** and resolves a relative path to absolute; it is deliberately **not** sandboxed, matching the documented position that a loopback-only server grants no filesystem access a local MCP client does not already have. - **FR-AGENT-24** (US-D2.7, issue #362, **history introspection**): the server exposes unauthenticated read-only **`get_history()`** reporting `undo_depth`, `redo_depth`, `next_undo_text` and `next_redo_text` - the same numbers and the same strings the GUI's Edit menu shows, read from the same global LIFO stack `undo`/`redo`/Ctrl+Z mutate. The tool **never pushes, pops or mutates** the stack: a test calls it three times in a row and asserts the three RETURNED `undo_depth`/`redo_depth` payloads are identical (comparing the values the tool returned, not the manager's state afterwards, which nothing in that path could have changed). - **FR-AGENT-25** (US-D3.2, issue #331, **succession domain intelligence**): the server exposes three unauthenticated read-only tools and one token-gated write. **`get_succession_plan(bed_id, year, today)`** returns a bed's slots date-sorted, the slot running on `today` (`current_entry`), the next one, the four season segments, and `reference_date` so the answer is reproducible; a bed with no plan reports `has_plan: false`, which is distinct from an empty plan, and a plan with no geo-location reports `coverage: "no_frost_dates"` **together with** month-based fallback segments and `segments_are_fallback: true` rather than an empty segment list. **`find_succession_gaps(bed_id, year, today)`** returns the growing-season ranges no slot covers, each with its season label and inclusive day count; a slot with unparseable dates covers nothing, so malformed data surfaces as a gap rather than reading as a full bed. **`suggest_succession(bed_id, gap_start, gap_end, candidates)`** ranks candidate crops, excluding any whose botanical family the bed already used earlier in the same plan or whose family is inside the 3-year rotation cooldown (reused from `CropRotationService.get_recommendation`), and any antagonistic to a concurrently-planted neighbour; `fits_window` is `false` for both "too slow" and "maturity unknown", distinguishable via `days_to_maturity`, and a too-slow candidate is returned ranked last rather than dropped. All three are Qt-free (`agent_api/domain.py`), accept an **injected** `today` so no assertion depends on the wall clock, and are deterministic — ranking ties break on `days_to_maturity` then `species_key`, and two tests pin both input-order reversal and repeat-call identity. **`set_succession_plan(bed_id, entries, year)`** replaces the bed's plan for the year (or deletes it when `entries` is empty/None) in **exactly one** undoable `SetSuccessionPlanCommand`, mirroring what the GUI's own succession dialog does. It is the **first agent write into `ProjectData` rather than the scene graph**, so every refusal leaves both `ProjectManager.succession_plans` **and** the undo stack untouched (asserted, including after a prior good write); it refuses an unknown bed, a target that is not a soil-capable bed (`is_bed_type`, so a TRELLIS is refused), overlapping ranges, non-ISO dates, `end_date < start_date`, and an unknown `species_key`. The segment windows used for gap arithmetic are made **disjoint** (each clipped to the day before the next begins), because the raw segments are contiguous and inclusive - filling the gaps this tool reports would otherwise be REFUSED as an overlap. `set_succession_plan` stores the **canonicalised** (lowercased) `species_key`, so a persisted plan matches every other per-species surface, while `suggest_succession`'s `candidates` accepts the case-insensitive display names `set_species` accepts. Season-segment boundaries were **extracted** from the succession dialog into `models/succession.py` so the GUI and the agent cannot disagree; the canvas badge refresh is inherited from the existing `succession_plans_changed` signal chain rather than duplicated. New prompt `plan-succession`. No `FILE_VERSION` change. See ADR-034/036 addenda and §8.19.
- **FR-AGENT-26** (issue #380, **agent writes are canvas-clamped**): an agent write can no longer create or move an object entirely off the plan canvas, where it would be invisible and un-deletable. The clamp rule lives **once** in the Qt-free `core/canvas_bounds.py` (`clamp_shift_within_canvas`, `clamp_delta_within_canvas`, `rect_intersects_canvas`) and is called by **both** the GUI drag/nudge clamp and the agent path, so the two cannot drift; a parity test asserts the GUI `_clamp_items_to_canvas` produces the same shift as the shared function. `create_object` clamps the whole creation group (a HOUSE and its ridge move together); `move_object`/`set_object_position` clamp the moved group (the item plus any plants it carries) and trim an offset that would strand it to the canvas edge; `BackgroundImageItem` stays exempt, matching the GUI. The gross-input guard (`require_reachable_position`) still refuses absurd coordinates (e.g. `1e9`) and leaves the scene **and** the undo stack untouched. A **pre-existing** off-plan object (e.g. from an older file) is made discoverable: `ObjectRef`/`ObjectDetail` gain `outside_canvas` (bounding-box based; true only when the box does not overlap the canvas at all), and `get_diagnostics` gains an **`outside_canvas`** kind. Every clamped write is still exactly one undo step; a move whose delta the clamp erases entirely is refused as a no-op rather than pushing a dead undo step. This is a deliberate reversal of the earlier documented “stage an object just off-plan” rationale. No `FILE_VERSION` change. See ADR-036 addendum and §8.19.
- **FR-AGENT-27** (US-D3.3, issue #332, **calendar & task tools**): the whole task engine — seven generators over the live plan — becomes reachable by an agent for the first time, answering "what should I do this week?". **`get_tasks(from_date, to_date, source, bed_id, species_key, include_dismissed, today)`** is unauthenticated and returns a curated list plus `coverage`, defaulting to a `today` ±30-day window; each task carries the generator's own fields **plus** two the engine does not store — `urgency`, computed at render time by `classify_urgency`, and `status`, read from the same shared store the Tasks tab uses. `urgency` and `status` are never re-implemented; `task_id` is the engine's own stable id, so an agent can name a task across calls. Filtering by `source`, `bed_id`, `species_key` and the date window each narrows, an **undated** task survives a filtered read, and `include_dismissed` reveals `archived` and `dismissed` — the **two statuses the Tasks tab hides**, so the agent is never a third surface disagreeing with the other two about one store. A plan with no geo-location reports `coverage: "no_frost_dates"` **together with** every non-calendar task (manual, succession, soil, frost): the calendar and propagation generators cannot run without frost dates, and an empty list would read as "nothing to do" when the truth is "the planting calendar could not be computed". `source` has **six** values for seven generators (both soil generators emit `soil`), so `task_type` carries the distinction `source` cannot. **`get_task_calendar(year, today)`** generates the complete requested year before month bucketing, independently of the urgency reference date; cross-year intervals are clipped to the year. Explicit `get_tasks` windows generate all dated tasks for their years before filtering, while the default keeps GUI reminder behavior. Propagation uses the shared GUI calculator, seed data and stored overrides. A task is counted in every month its window touches. **`add_manual_task` / `edit_manual_task` / `delete_manual_task`** are token-gated writes, each exactly one undo step, and **generated tasks are refused by name** — they are derived state rebuilt on every read, so editing one would be undone by the next call. **Agent task-status mutation is deliberately not exposed**: `ProjectManager.set_task_status` is not a command, so it would be the one agent write a single Ctrl+Z could not reverse. The `plan-my-week` prompt composes the window, the month overview, the plan summary and the open diagnostics into a prioritised seven-day brief, and states the missing-location case explicitly rather than presenting an empty week. Qt-free (`agent_api/domain.py`), accepts an **injected** `today` (threaded through a new `build_plan_state(today=...)` parameter that defaults to the wall clock), and is deterministic — tasks sort on `(start_date, task_id)`. No `FILE_VERSION` change. See ADR-034/036 addenda, §8.19, §11.4.
- **FR-AGENT-28** (US-D3.4, issue #333, **soil amendment tools**): the agent can report *and* fix a soil problem, closing the gap where `get_diagnostics` could say a plant disagreed with its soil but not what the reading was or what to do about it. **`get_soil_status(bed_id, today)`** is unauthenticated and returns the bed's **effective** record with **`record_source`** (`bed` / `global` / `none`) alongside it — `SoilService.get_effective_record` applies its hierarchy (own latest → plan-wide default's latest → none) and returns the record alone, so without the provenance an agent would attribute a plan-wide assumption to a bed that was never tested. pH and per-nutrient kit levels carry `health_level` straight from `SoilService.health_level`, including its "worst non-unknown wins" rule; `overall_health_level` covers **pH and N/P/K only** (the engine's own scope), and a secondary nutrient reports `health_level: null` meaning *no rating exists* — because passing `'ca'`/`'mg'`/`'s'` to the service falls through to its `overall` branch and would report the whole bed's health as calcium's. `is_test_overdue` uses the matching effective-record history, including global fallbacks. Status returns a `beds` list for one/all beds; mismatches return a bed-UUID-keyed `beds` mapping with per-bed coverage and aggregate no-beds/no-test/partial/ok coverage. **`recommend_amendments(bed_id, today)`** curates `calculate_amendments` field for field — a wrapper, never a second computation — with `quantity_g` already scaled to the bed's area, and pairs a stable `amendment_id` with a `display_name` selected by the existing bilingual display-name method using the app's current language. **`get_soil_mismatches(bed_id, today)`** returns the plants behind the mismatch flags `get_diagnostics` already reports, as `reason_codes` (`ph_low`, `ph_high`, `n_high_demand`, `p_high_demand`, `k_high_demand`) beside positional display sentences, from one canonical builder shared with the canvas overlay. An untested bed reports `coverage: "no_soil_test"` — *untested*, never *healthy*. **`record_soil_test(...)`** is token-gated and takes the **Rapitest kit scale only**: `n_level`/`p_level` `0–4`, `k_level` **`1–4`** (the kit has no K0), `ca_level`/`mg_level`/`s_level` `0–2`, `ph` `0.0–14.0`, strictly typed at the MCP boundary (booleans and numeric strings are refused), each validated against its own range in **exactly one** undoable `AddSoilTestCommand`. **Lab ppm values are refused by name**: nothing in `services/` reads the `*_ppm` fields and no code converts between the scales (US-12.10c), so a ppm-only record would report UNKNOWN health, recommend nothing and find no mismatches while looking complete. Every refusal — out-of-range level, non-finite or implausible pH, unknown or non-soil bed (a TRELLIS is refused via `is_bed_type`), bad texture, malformed or future date, or no reading at all — leaves `ProjectManager.soil_tests` **and** the undo stack untouched. The `plan-soil-amendments` prompt asks for a test when there is none. Qt-free, reproducible via an injected `today`. No `FILE_VERSION` change. See ADR-034/036 addenda, §8.19, §11.4.
