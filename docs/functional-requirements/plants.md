# Plants

## Plant objects and species data

- **FR-PLANT-01**: Plants rendered as illustrated SVG shapes (species-appropriate)
- **FR-PLANT-02**: Visual distinction between trees, shrubs, perennials, annuals
- **FR-PLANT-03**: Optional label showing name/species
- **FR-PLANT-04**: Visual indicator for plant status (healthy, needs attention, planned)
- **FR-PLANT-05**: All metadata fields editable in properties panel
- **FR-PLANT-06**: Species field supports autocomplete from plant database
- **FR-PLANT-07**: When species selected from database, default values populated
- **FR-PLANT-10**: Connect to Trefle.io API for plant species lookup (primary)
- **FR-PLANT-11**: Offline mode: cache previously fetched plant data locally (SQLite)
- **FR-PLANT-12**: User can create custom plant species entries (stored in local library)
- **FR-PLANT-13**: Search plants by common name, scientific name, or characteristics

- **FR-PLANT-14**: Species search first queries the complete bundled/custom offline catalog, then applies the text and trait filters before the display limit. Empty or filter-only browsing stays offline. A nonempty query with zero filtered offline matches automatically invokes the configured online fallback chain; **Search online** invokes it explicitly even when local matches exist. Online requests and selected-result enrichment run away from the GUI thread, with obsolete query/selection/closed-dialog responses discarded.

  The existing `PlantAPIManager.search()` online fallback still searches custom entries before Trefle, Perenual and Permapeople. It does not deduplicate custom-library results against provider results. Every result row shows its source (FR-PLANT-18), distinguishing a reusable user record from a fetched record. The bundled catalog is available through the shared offline search service rather than a new network-manager client.

- **FR-PLANT-15** *(issue #170)*: On canvas drop or tool draw of a plant, look up the species in the bundled DB (`resources/data/plant_species.json`) by scientific name → common name → alias (case-insensitive). On hit, populate `metadata["plant_species"]` with the full record (pH, NPK demand, sun, water, calendar, hardiness) so the plant detail panel shows data immediately and US-12.10d soil-mismatch warnings fire automatically. A **gallery** drop of a named species also sizes the drawn footprint so its diameter equals the species' `max_spread_cm`, exactly like a Plant Database drop (`build_species_plant`); an unknown/custom name keeps the gallery default (TREE 200 cm, SHRUB 100 cm, PERENNIAL 60 cm). This is creation-time sizing only — an existing plant's footprint still changes only through a species assignment (FR-PLANT-17), and the 2D/3D canopy of an unmeasured plant follows its drawn footprint, so resizing or clearing `max_spread_cm` never rewrites owner geometry. (#596 manual pass: the fixed gallery diameter made an 8 m apple tree 2 m wide in 3D.)
- **FR-PLANT-16** *(issue #170)*: Bundled DB ships records for **every species exposed by the gallery** (currently 123 entries: trees, shrubs, vegetables, herbs, berries, fruits, ornamentals). Every record has `ph_min`, `ph_max`, `nutrient_demand`, `n_demand`, `p_demand`, `k_demand` populated. Where the gallery's species string differs from the canonical common name (e.g. "pea" vs "Garden Pea", "apple tree" vs "Apple Tree"), records carry an optional `aliases` array. Misses fall through to the existing API search button (FR-PLANT-14).
- **FR-PLANT-17** *(issue #213)*: Assigning a database species to an **existing** generic plant — via the plant database panel (Load Custom / Create Custom) or the Plants-menu species search (`application.py`) — writes `metadata["plant_species"]` **and** resizes the drawn footprint so its **diameter equals the species' `max_spread_cm`** (the visible change the issue requires) while keeping the plant centred. The resize is **silent** in the common case; the only thing that prompts is a **manual `spacing_radius_cm` override that conflicts with the database value** — then a dialog offers **Apply database values** (default: resize the footprint and clear the override so the database cascades) or **Keep custom values** (override *and* placed footprint left untouched). The assignment is a single undoable step (`ApplySpeciesCommand`, one undo unit, dirties the document — metadata, override, and footprint radius all revert together). Species with no usable `max_spread_cm` only update metadata (no resize). The footprint is resized via `CircleItem.set_radius_centered()`, which keeps the rotation pivot on the new centre so a rotated plant does not drift on save/reload.
- **FR-PLANT-18** *(issue #297)*: Confirming a plant search result in `PlantSearchDialog` (OK or double-click) fetches the provider's full per-species detail record via `PlantAPIManager.get_by_id()` and merges it onto the search result before it is assigned to a plant. The merge is generic (`_merge_detail_into_search_result()`, a loop over every `PlantSpeciesData` field): a field at its dataclass default — or `None`, regardless of the field's own default — in the detail response defers to the search result's value; every other field takes the detail response's value. `source_id`/`data_source`/`raw_data` always come from the detail response. Search/list endpoints can be structurally sparser than detail endpoints for the same provider — confirmed live for Trefle's `/plants/search`, which omits `growth`/`specifications`/`foliage` entirely, so `sun_requirement`, `water_needs`, `ph_min`/`ph_max`, `nutrient_demand`, `foliage_color`/`foliage_texture`, and (also detail-only) `max_height_cm`, `growth_rate`, `description` would otherwise stay at their unset defaults for every Trefle-sourced plant regardless of parser correctness. The fetch runs once, on confirm, not per browsed result (rate-limit consideration); is skipped for anything that isn't a known online provider (`data_source` not in `{"trefle", "perenual", "permapeople"}`, or an empty `source_id`) -- local custom/bundled entries and unidentifiable results have no online detail endpoint to fetch. **Two failure modes, two behaviors**: a provider signaling "no richer detail exists for this record" — `PlantDetailUnavailableError`, raised for Perenual's free-tier paywall (HTTP 429, live-confirmed not rate limiting) and for Trefle records with a present-but-null `main_species` (~4% of a live sample, all scientific-name-only species) — falls back **quietly** (logged, no user-facing warning), since nothing is actually wrong. A genuine failure — a raised error, or a successful response whose `source_id` doesn't match the one requested — shows a translated warning before falling back, so a real failure can't silently reproduce #297's own symptom. Deliberately does **not** reject on an empty/missing `common_name` alone: Trefle omits it for many genuinely valid, scientific-name-only species, and a first cut of this fix wrongly discarded fully-populated detail records on that basis (caught in senior review round 2). **Enrichment gain is provider-dependent** (measured live, senior review round 7): Trefle's detail response consistently adds `description`/`sun_requirement`/`water_needs`/`ph_min`/`ph_max`/`nutrient_demand` over its search response, but Perenual's and Permapeople's detail responses did not carry any field their own search responses lacked in the sample checked — so a confirm against those two providers still requests a detail round-trip without a measured data gain in that historical sample. Acceptance now fetches details on a worker while the dialog remains responsive. Changing the selection, starting another query or closing the dialog invalidates the pending response; only enrichment for the current selection can complete acceptance. Not a bug (their parsers may grow to use more detail-only fields later), but worth knowing before assuming every provider benefits equally. **Manual-testing finding (2026-08-10)**: a result row previously showed only `"{common_name} ({scientific_name})"`, with nothing indicating which store served it. Since the custom library is searched first (FR-PLANT-14) and is not deduplicated against API results, a stale or bogus custom entry sharing a name with a real species was visually indistinguishable from -- and silently shadowed -- the live API record; confirming it skipped enrichment entirely (`data_source == "custom"`) with no explanation shown. Every result row now shows its data source (e.g. "Tomato (Solanum lycopersicum) — Custom Plant" vs "— Trefle") via the shared `plant_source_label()` helper (`ui/plant_species_assignment.py`), also used by the properties panel's own "Data Source" tooltip so the two can't drift apart. **File-size consequence, documented not fixed (final review pass, 2026-08-11)**: `raw_data` (the full provider response, kept for `"Extensible metadata for API-specific fields"` per its own field comment) is one of the three fields `_merge_detail_into_search_result()` always takes from the detail response, deliberately and pinned by `test_source_id_data_source_and_raw_data_always_come_from_detail`. Before this fix, a Trefle-sourced plant's persisted `raw_data` was the sparse search-result payload (enrichment never ran); after it, a successfully enriched plant persists the full detail response instead -- larger, but not a new category of data: every provider's `search()` result was already persisting its own raw API response the same way. No code currently reads `raw_data` back for any provider. Left as-is rather than stripped, since removing it would contradict the existing, deliberately-tested "detail's raw_data is the richer payload" invariant on a doc-and-hygiene finding -- revisit only if `.ogp` file size becomes a measured problem.
- **FR-PLANT-19**: Species snapshots carry seven food-forest layers plus unspecified and twelve recorded functions; Permapeople Layer/Uses ingestion, conservative sourced bundled facts and selected-plant undoable edits preserve unrelated fields and custom library records.
- **FR-PLANT-20**: Search/gallery combine text, OR layer chips and all-selected function chips. - **FR-PLANT-21** *(issue #445)*: Assigning a species from the plant database writes the item's own **species string** as well as the record, so the plant is **drawn** with that species' sprite - in 2D and in 3D alike. The string is what the sprite resolver reads; the record's data is what the calendar, the sizing and the diagnostics read. The name written is the name of the species **assigned**: the record's common name, or its scientific name when the common name names no sprite. The string is the plant's own name - the gallery writes it when the plant is created, and an assignment replaces it with the species assigned - so the string and the record's data can still differ (a gallery "Pumpkin" carries the data of "Winter Squash" while its own string is "pumpkin"), and the resolver reads the **string**, never the record's name. The assignment stays one undoable step - the record, the spacing override, the footprint radius and the string revert together (FR-PLANT-17). Undoing the last species assignment also clears the profile name, thumbnail, external links and attribution; redo restores them. A species-free selected plant remains available to Create Custom.
- **FR-PLANT-22** *(issue #559)*: Every committed **Plant Details** species-field and instance-field edit is **one undoable step** (`PlantSpeciesEditCommand` / `PlantInstanceEditCommand` through the shared `CommandManager`), and undo/redo restores metadata, geometry, display and diagnostics together. Numeric spin gestures coalesce: consecutive ticks of one drag merge into the pending command. Free-text notes coalesce through a debounce and flush before selection change or teardown. A no-op edit adds no history entry. Species edits never undo the shared custom-library side effects (`update_plant` / `add_plant`), which are documented as explicitly separate. The bundled calendar overlay (`merge_calendar_data`) fills calendar fields but never overwrites the two form-owned fields it also covers (`family`, `nutrient_demand`): on this edit path the committed widget values win.
- **FR-PLANT-23** *(issue #558)*: Editing **Max Spread** on a plant whose displayed size derives from species dimensions resizes the 2D canopy footprint diameter and the 3D canopy spread together, preserving center and rotation pivot in one undo step. Precedence: an explicit spacing override, an explicit current/measured spread, or a custom footprint (drawn radius differing from the old species size) wins and the edit resizes nothing; growth-date scaling and manual spacing overrides are never silently discarded. A cleared maximum preserves the current geometry instead of collapsing it. Setting a real width replaces any estimate immediately.
- **FR-PLANT-24** *(issue #302)*: A plant search that every reachable database answers with **zero matches is not an error** and must never be reported as one. `PlantAPIManager.search()` raises `PlantAPIError` only when *no* configured provider answered at all (every one raised) and the custom library had no hit; if at least one provider answered — even with an empty list — the honest result `[]` is returned. `PlantSearchDialog` then shows a warning-coloured status *"No plants matched '{query}'. Try another spelling or the scientific name."* with **no modal dialog**, or *"No plant databases are configured. Add API credentials in Preferences to search online."* when `PlantAPIManager.configured_source_count == 0`. If one configured provider answered with zero matches while another *raised*, the result is still an honest zero result (no modal) but the status appends *"({sources} unavailable — check Preferences.)"* naming the failed provider(s) (`PlantAPIManager.last_search_failed_sources`), so an outage is not silently masked by a neighbour's empty answer. The red *"Search failed: …"* status plus the *"check your internet connection and API credentials"* message box is reserved for a genuine technical failure (every configured provider raised). (Before this, a query for a variety absent from every database — the reporter's *mahachanok* mango — produced the failure dialog with the credentials hint even though connection and credentials were fine; the same misreport class the #294 Preferences "Test" button had.) Pinned by `tests/integration/test_plant_search_zero_results.py` and `tests/unit/test_plant_api_manager_search.py`.
- **FR-PLANT-25** *(issue #1002; [Discussion #983](https://github.com/cofade/open-garden-planner/discussions/983); follow-ups #1001/#1003/#1005)*: The main toolbar's **Plant Grid** tool places a rectangular grid of one species on the 2D plan. The first click on the plan opens the rows-and-columns dialog (1-20 each; the last confirmed counts are remembered) and then the plant database search. That search uses the same Preferences credentials as **Search Plant Database**. The first click is one corner; the second click sets the opposite corner. The draft can then be moved, resized and rotated on the canvas. Its control strip edits the counts or the species, switches between outlines and a species preview, and shows a plant-size slider. The strip's size, spacing, width and height fields are units-aware: they display the active unit profile and accept typed values, while the plan stays in centimetres (ADR-078/081). Typing the column spacing sets both axes; typing an extent keeps the centre and updates the column-spacing readout (the row pitch is `Height ÷ rows`). The size slider and the orange size handle set **one plant diameter for every plant** in the grid. A chosen size is a drawn footprint, like a resized single plant, never a measured current spread, so a plant's modelled height is unchanged (FR-PLANT-23). With snapping on, a move snaps the draft's centre, a resize snaps its dragged edge and rounds the per-cell spacing to whole centimetres while keeping the opposite edge, a rotation within 3° of a 15° step sticks to it (Shift always snaps), and the size handle rounds to whole centimetres. Confirm places the plants through `CreateItemsCommand`, which links each plant to the bed under its centre. Placement is one undo step, with an optional group in the same step (the grouping question defaults to No; Cancel returns to the draft). The new plants or their group are then selected. Moving that group out of a bed re-links its plants in the same undo step as the move. Every plant centre must lie inside the plan, or the confirmation is refused with a status message. Esc, the Cancel-grid button, a tool switch or a replaced plan discard the draft; a pinch keeps it (ADR-082). The tool has its own `plant_grid.svg`; the generic grid glyph keeps the grid-visibility and rows-and-columns meanings.

## Plant guilds

- **FR-GUILD-01**: Versioned bundled/user templates, New/Duplicate/Edit/Reload, atomic UTF-8 saves, eligibility validation and visible malformed-file errors support at most 200 plants per stamp. Bundled templates remain read-only.
- **FR-GUILD-02**: New/existing-centre insertion preflights mature-spacing/numeric ring layout, all species/layers and boundaries before one undoable command. Cancel/refusal makes no plan/history mutation.
- **FR-GUILD-03**: Explicit metadata membership remains independent of Qt groups and plant parents. Coverage counts recorded functions once per assigned plant; multifunctional members may cover multiple roles. Existing instances retain template snapshots. Centre deletion dissolves surviving links in the same undo step; complete copies remap IDs and partial copies omit membership.
- **FR-GUILD-04**: Centre badges, Companion Guilds and the general Diagnostics panel share computed guild warnings with MCP. Malformed saved guild metadata is preserved and excluded with a data warning. UUID navigation and idempotent debounced refresh avoid stale item references and repaint loops.

- **FR-LIB-02**: Template / entry includes: name, scientific name, default geometry, snapshot botanical data (`PlantSpeciesData`), and user notes.
- **FR-LIB-03**: Library stored locally, persists across projects in `<app-data>/plant_lists.json` using atomic replace writes.
- **FR-LIB-04**: Drag species from list to canvas to create instances with auto-parenting to underlying beds, proper sizing, today's planting date stamped, and single-step undo.
- **FR-LIB-05**: "Update from plan" allows user-confirmed, explicit snapshot refresh from placed plants (no silent automatic overwrites).
- **FR-LIB-06**: Import/export plant lists as standalone JSON files for sharing.
- **FR-LIB-07**: Read-only Agent API (MCP) resource `garden://plant-lists` exposes catalogs of lists and entries to AI assistants.

## Plan timeline and plant lifetimes

- **FR-TIMELINE-01**: One shared local plan date controls month scrubbing, Today,
  exact calendar dates, plant presence, sprite/3D growth and solar analyses.
- **FR-TIMELINE-02**: Optional removal dates round-trip additively; valid planting
  and removal edits each have one undo step and reject inverted/empty lifetimes.
- **FR-TIMELINE-03**: Plants before planting or on/after removal are hidden and
  unselectable; date-present data diagnostics exclude them independently of drawing
  layer visibility. Solar analyses also honor visible layers. A named-date popover permits
  discovery and navigation. A non-today indicator identifies the viewed date.
- **FR-TIMELINE-04**: Visual exports reflect current visibility; PDF reports identify
  a non-today date. Print uses the same current-map readiness and animation pause,
  validates each preview paint and labels the plan date. API objects retain absent plants and expose presence/as_of_date.
- **FR-TIMELINE-05**: Viewing dates never deletes plant data or changes yearly Season
  Manager copies. Generated plant tasks stop after removal, with surviving instances
  retaining a species schedule; manual tasks and succession dates remain independent.
- **FR-TIMELINE-06**: Plan & Sun date/time editor steps carry and borrow through
  month/year, hour/day and minute/hour boundaries in both directions, including
  held arrows, wheel and spin buttons. Calendar month/year steps retain the preferred
  day through shorter months and leap years. Each step publishes one complete naive
  wall reading to SimClock; only its absolute supported range saturates navigation.
- **FR-TIMELINE-07**: Without garden coordinates, Plan & Sun shows a location hint
  beside Hours of Sun that opens the existing Set Garden Location dialog. It remains
  visible until coordinates are set, including after cancellation and document
  replacement. Configuring coordinates automatically resumes an enabled sun map.
